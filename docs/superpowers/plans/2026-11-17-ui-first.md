# UI-First: every command and setting of ours works from the hub Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A player never types one of our commands, and an OP never edits a toml, to use anything the mod adds. Player actions get hub buttons; a new hub page **Admin**, shown only to OPs (permission level >= 2, checked again on the server), holds the common config, the debug actions and (none today) the gamerules; a small **Settings** page holds each player's own client settings.

**Architecture:** Pure rules in a new package `shared.admin` (access check, value check, the allow-list of settings, the table of command forms). A server payload `AdminSetPayload` is the only way the hub changes a setting: the handler checks permission, looks the id up in the allow-list, checks the value against the real `ModConfigSpec.ValueSpec`, calls `ConfigValue.set` then `ModConfigSpec.save()`. Debug actions keep running as the typed command (`connection.sendCommand`, the way every hub button already does), so Brigadier's `.requires(hasPermission(2))` is the server check. The page is a normal `HubPage` with a view per theme built on `Detail`, `FocusOrder`, `ConfirmModel` and `Narration`. Coverage tests make a new command or config key fail the build until it has a UI entry.

**Tech Stack:** Java 21, NeoForge 21.1.265, Minecraft 1.21.1, JUnit 5, GameTests.

**Spec:** `docs/superpowers/specs/2026-11-17-ui-first-audit.md` (the full list of commands, keys and what the hub has today; row ids B1..B7, P1..P15, D1..D10, C/V/S/H/A/X/T/U below refer to it).

## Research result (checked in the Gradle cache, not guessed)

Source: `neoforge-21.1.265-sources.jar` (`ModConfigSpec.java`) and `net.neoforged.fancymodloader:loader:4.0.45` (`javap -c` of `LoadedConfig.save`).

- `ConfigValue.set(T)` writes into the loaded config and updates the cached value only when `RestartType == NONE`. It **does not validate**, fires no event and does not write the file. So we must call `valueSpec.test(value)` first (`ConfigValue.getSpec()` and `ValueSpec.test`, `getRange()`, `getDefault()`, `restartType()` are public; `test` includes the range and the `defineInList` and custom validators).
- `ModConfigSpec.save()` throws `NullPointerException` if the config is not loaded (`isLoaded()` is the guard). It calls `LoadedConfig.save()`: writes the toml (`ConfigTracker.writeConfig`), then fires `ModConfigEvent.Reloading` under the config lock. Our `ConfigWarning` already listens to `Reloading`.
- `ConfigValue.get()` is cached; the cache is reset by `afterReload()` only for `RestartType.NONE`. `RestartType` is `NONE`, `WORLD`, `GAME` (`GAME` is not allowed for `SERVER` configs). **We declare none of `worldRestart()` or `gameRestart()`, so NeoForge treats all 67 of our keys as live.**

### Live or restart

| Type | Change from the hub | Takes effect |
|---|---|---|
| COMMON (60 keys, files in `config/`, per JVM, never synced) | server payload, `set` + `save` on the server | **live** on the server for every key that is read at its point of use (all but C1-C9). C1-C9 `parts.*` are read once by `EarlySwitches` before any spec loads and by the mixin plugins: **restart the server** (in single player: the game). T1, T3, T4 are also read by each client from its own file: **the server's change does not reach clients**. |
| CLIENT (7 keys) | local `set` + `save` on the client (as `HubClientConfig.setTheme` does) | live |
| SERVER (none of ours) | would be the same server `set` + `save` | NeoForge copies the file to clients when they connect (`ConfigSync.syncConfigs`); whether a later change is re-sent was not verified. Not needed: we have none |
| `RestartType.WORLD`/`GAME` (none of ours) | `set` leaves the cache untouched | only after the world or game restarts |

## Global Constraints

- Parts never import each other. The registry and the rules live in `shared.admin`; each part registers its own spec (`AdminSpecs.register(FILE, SPEC)`, next to its `registerConfig`) so a disabled part adds nothing and its spec class is never loaded.
- The hub lives in the `supernatural` part. With that part off (or Vampirism missing) there is no hub and so no Admin page. Commands still work. See the open questions.
- Server authority: every payload and every command re-checks permission and range on the server. The client's `hasPermissions(2)` only decides what to draw.
- Pure first: the access check, the value check, the allow-list and the command table have no game classes (as `PayloadCaps`, `FocusOrder`).
- Text in `lang/en_us.json` (the only language file), 8 GUI px minimum, contrast by the existing `ThemeContrast` tests, the three themes are all done (Grimoire, Blood Moon, Tensura).
- Reserved key H5 (`hide_in_controls_mixin`) stays out of the UI (`hidden` with a reason).
- Tests run with `--no-daemon`; the game-test script is `C:\Users\caiom\AppData\Local\Temp\opencode\gm.ps1` (`pwsh -NoProfile -File ...\gm.ps1 -TimeoutSec 900 runGameTestServer`; it runs the checkout hard-coded in the script). The unit tests are `gradlew.bat --no-daemon test`.

## Review Focus

- A level-1 or level-0 sender can never change a value: payload refused, no `set` call, no file write, nothing leaked in the reply. Pinned by `AdminGameTests.nonOpPayloadIsRefused`.
- An id not in the allow-list (including H5, client keys and a made-up path) is refused. A value of the wrong type or outside the range is refused and the old value stays.
- A refused edit never half-applies: `set` happens only after `test`, and a failed `save` is reported, not swallowed.
- Restart-required rows say so before and after the change (C1-C9).
- A key or command added later without an entry fails a test, with the name in the message.
- P2: the hub's `[Accept]` really accepts (the broken token-less command).
