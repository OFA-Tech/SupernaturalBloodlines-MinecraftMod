## Task 1: Pure multi-type computation (`MultiTypes`)

**Files:** Create `core/group/MultiTypes.java`; test `core/group/MultiTypesTest.java`.

**Interfaces:**
- `MultiTypes.of(GroupTypes.Leader) -> Set<GroupType>` (the table from design §1.2).
- `MultiTypes.mainType(Set<GroupType>) -> GroupType` (first in canonical order PACK > CLAN > COVEN > BROTHERHOOD).
- `MultiTypes.fits(GroupType, ServerPlayer) -> boolean` (per-type fit: pack=all, clan=vampire-like, coven=witch-like, brotherhood=human/hunter). Ascension Bloodfiend counts as vampire-like. Witch-hunter fits both coven and brotherhood.

**Tests:** One `@Test` per row of the type table; one per fit rule; `mainTypeIsDeterministic`; `emptySetGivesPack` (fallback); `ascensionBloodfiendIsVampireLike`; `witchHunterFitsBoth`.

**Commit:** `feat(groups): pure multi-type computation`.

## Task 4: Member removal on type-set change

**Files:** Modify `GroupSwitcher.java`; test `GroupSwitcherMultiTypeTest.java`, `gametest/GroupMultiTypeSwitchGameTests.java`.

**Interfaces:**
- `GroupSwitcher.refresh` returns `Optional<SetChange>` (record with old/new sets) in place of `Optional<Switch>`. Hooks receive `SetChange`.
- After type-set change, members who fit none are removed after `type_lost_grace_seconds` grace (wall-clock, transient map in `GroupSwitcher`). Notice: `group.type_lost.<lastFitType>`. Offline members get queued notice.
- Grace resets on each type-set change.

**Tests:** `memberWhoFitsNoneIsRemovedAfterGrace`; `graceResetsOnSecondChange`; `offlineMemberGetsQueuedNotice`; `memberWhoFitsOneTypeStays`; `circleClosedWhenCovenLeaves`; `contestVoidedWhenClanLeaves`; `voteCancelledWhenCovenLeaves`; `switchBackRestoresDormantRows`; `runningEventsVoidedOnReturn`.

**Commit:** `feat(groups): member removal on type-set change with grace period`.

## Open Questions

| # | Question | Recommended pick | Rationale |
|---|---|---|---|
| Q1 | Should the grace period apply when a member is kicked manually, or only on type-set change? | Only on type-set change. Manual kicks are intentional and immediate. | Keeps kick semantics unchanged; grace is for involuntary loss of fit. |
| Q2 | Should the hub cycle order be configurable? | No. Canonical order (PACK > CLAN > COVEN > BROTHERHOOD) is deterministic and matches main-type priority. | Config adds complexity for no gameplay benefit. |
| Q3 | Should NPC subordinates count toward circle tier thresholds (3/7/13)? | No. Tiers gate grand rites; NPCs add potency only. | Owner decision implied by "add potency" wording. Tiers stay member-only. |
| Q4 | Should a member who fits multiple types get perks from all of them simultaneously? | Yes. A witch-vampire in a pack+clan+coven gets circle link, shared feeding, and arms bonus if they also fit brotherhood. | Owner decision #1251: "each member gets only perks of types they personally fit." Multiple fits = multiple perks. |
| Q5 | Should the `multi_type_groups` config switch affect existing groups immediately on reload? | Yes, via the next sweep. No bulk operation. | Consistent with how other config switches work (e.g., `clans_enabled`). Sweep is already periodic. |

All recommended picks are reflected in the design doc. If any are rejected in the course of review, update the design doc before implementation.
