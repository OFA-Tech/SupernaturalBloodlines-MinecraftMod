# Mixins

Every mixin must be listed here. Budget: at most 3 per part, each `require = 0`, gated by that part's switch.

Convention: one mixin config and one `IMixinConfigPlugin` per part. The config is `supernaturalbloodlines.<part_key>.mixins.json` (the part key in snake_case), the plugin is `<Part>MixinPlugin` in `net.ofatech.supernaturalbloodlines.mixin`, and the mixin classes live in `mixin.<part>` (no separator, like the part package). The plugin applies the config only when all of `Part.requiredMods()` are installed and the part's switch is on (read through `EarlySwitches`, from the toml file, because COMMON configs load after mixins). Otherwise nothing is touched.

## vampirism_tensura (3 of 3)

Config `supernaturalbloodlines.vampirism_tensura.mixins.json`, plugin `VampirismTensuraMixinPlugin`, package `mixin.vampirismtensura`. Applies only when Vampirism and Tensura are installed and `parts.vampirismTensura` is not `false` in `supernaturalbloodlines-common.toml`. The plugin logs one line saying whether the mixins were applied.

| Part | Mixin | Target | Why | Config switch |
|---|---|---|---|---|
| vampirism_tensura | `VampireRaceSunMixin` | `VampireRace.shouldBurn(LivingEntity)` (HEAD, returns false) | Tensura has no config option for its vampire burn (checked in `VampireConfig`). A player in the Vampirism vampire faction already takes Vampirism's sun damage, so Tensura's fire would be a second burn. Also called from `GhoulRace`/`WightRace`, so it is gated on "player is in the Vampirism vampire faction" (`VampireSunRule`). Skipping `shouldBurn` also skips the helmet damage. | `parts.vampirismTensura` |
| vampirism_tensura | `VampirePlayerBiteMixin` | `VampirePlayer.determineBiteType(LivingEntity)` in Vampirism (HEAD, returns `BITE_TYPE.NONE`; string target, because only the Vampirism api jar is on the compile classpath) | A vampire must not bite a player whose Tensura race has the race tag `tensura:no_blood`. Checked first: `BloodDrinkEvent` is not cancellable (`setAmount(0)` only changes what the biter gets, the victim has already lost food by then), the bite starts from a custom network packet (`ServerboundStartFeedingPacket`), not a NeoForge interaction event, and the player blood value has no data map or capability to override (the `entity_blood` data map only covers mobs). Only fires when the victim is a player with a bloodless race. | `parts.vampirismTensura` |
| vampirism_tensura | `RaceUtilsSunMixin` | `RaceUtils.isUnderSun(LivingEntity)` (HEAD, returns false) | `VampireRace.onTick` adds Weakness, Slowness and Mining Fatigue (amplifier 3) whenever `isUnderSun` is true, before it ever calls `shouldBurn`. Faction vampires skip them too: Vampirism's sun handling wins (its own sun damage, nausea and weakness by level). The same method gates Tensura's bat form under sun, so a faction vampire may use it by day. Only faction-vampire players are affected; the night/moon-phase branch of `onTick` is unchanged. | `parts.vampirismTensura` |

## species (3 of 3)

Config `supernaturalbloodlines.species.mixins.json`, plugin `SpeciesMixinPlugin`, package `mixin.species`. Applies only when Vampirism and Enchanted are installed and `parts.species` is not `false`. The witch bonus has its own switch, `witch_bonus_enabled` in `supernaturalbloodlines-species.toml`: if an Enchanted update makes a mixin miss (`require = 0`), the bonus is simply missing and the log says so; the switch turns the bonus off on purpose.

| Part | Mixin | Target | Why | Config switch |
|---|---|---|---|---|
| species | `AltarRangeMixin` | `AltarBlockEntity.firstTick`, `setupBlockData`, `posWithinRange` (`@Redirect` of `ServerConfig.altarRange.get()`; a `@Unique` field keeps the first answer) | R61: altar range x1.5 when a witch, heretic or tribrid stands within the altar's normal range as the altar loads (`WitchAltarBonus.rangeFor`). The altar has no owner, so a nearby player is the only thing to look at. The three reads must agree or the altar's block count drifts (a block added while the range was wide, removed while it was narrow), so the range is decided on the first read with a level and kept until the altar reloads: a witch arriving later does not widen it, one leaving does not narrow it. | `species`, `witch_bonus_enabled` |
| species | `RiteCostMixin` | `GoldChalkBlockEntity.serverTick` (start cost: `@ModifyVariable` of the local `power`, `@Inject` after `Rite.start()` and at `RETURN`) and `tryConsumePower(int)` (per-tick cost: `@ModifyVariable` of the argument); also implements `ChalkCaster` to expose the private `caster` | R61/R62: cost x0.75 when the caster, or the player on the circle's centre, is a witch type near a linked altar. Only the one-off start cost is then paid from the caster's siphoned power first (`RiteCost`); per-tick costs get the discount only, so siphoned power never syncs every tick. A start cost of 0 skips Enchanted's altar check completely, so a siphoner whose siphoned power covers the rite needs no altar. The siphoned power is taken after `Rite.start()` returned, and not if the rite cancelled itself (`RiteCancelMixin`). | `species`, `witch_bonus_enabled` (cost x0.75 only; siphoned power is always used) |
| species | `RiteCancelMixin` | `Rite.cancel()` (HEAD) | A rite that refuses its target in `onStart` (wrong faction, the rules say no) calls `cancel()`; this drops the pending siphoned power so the refused siphoner pays nothing. | `species` |

## species_tensura (2 of 3 so far)

Config `supernaturalbloodlines.species_tensura.mixins.json`, plugin `SpeciesTensuraMixinPlugin`, package `mixin.speciestensura`. Applies only when Vampirism, Enchanted and Tensura are installed and the species and species_tensura switches are on (the plugin uses the same `PartLoader` rule as the part itself, so a part whose required part is off gets no mixins). The plugin logs one line saying whether they were applied.

| Part | Mixin | Target | Why | Config switch |
|---|---|---|---|---|
| species_tensura | `RaceUtilsMixin` | `RaceUtils.isUndead(Entity)` and `RaceUtils.isAffectedByHolyExposure(Entity)` in Tensura (HEAD, returns true) | R100: a species whose layer says `treatAsUndead` (and a plain Vampirism vampire) counts as undead for Tensura: holy and light damage x3 (`DamagingHandler`), holy exposure, infection and so on. Both methods are plain static checks with no event, no gamerule and no config (verified with javap, docs/parts/species_tensura.md). `isBloodless` is not touched (it never reaches `isUndead` for a living entity). Only a `Player` is affected, and only when `UndeadTreatment.applies` says so. If Tensura renames the methods the injection is skipped (`require = 0`) and the layers keep granting skills and bonuses. | `undead_treatment_enabled` in `supernaturalbloodlines-species_tensura.toml` (the mixin stays applied, the check returns to Tensura's own answer) |
| species_tensura | `RaceInstanceMixin` | `ManasRaceInstance.getNextEvolutions(LivingEntity)` and `getEvolutionProgress(LivingEntity, ManasRace)` in ManasCore (both `@At("RETURN")`, `cancellable`, `require = 0`) | R100: the one common-code place that the evolution screen's list, "set tracked" and the server's `contains` check all call, so adding the species' apex race to the (immutable) list makes it pickable and valid server side (`ApexOffer`). The same mixin scales the reported progress toward any evolution for a player with a species (`EvolutionBoost`, x1.25, capped at 100): Tensura reads requirements live from the player, so there is no per-requirement hook. The plugin looks for both calls in `postApply` and logs `RaceInstanceMixin hooks in place` or a warning per missing hook; the part logs a warning at init when the apex hook is missing. | `apex_evolutions_enabled` (apex offer), `evolution_progress_multiplier` (1.0 turns the bonus off) in `supernaturalbloodlines-species_tensura.toml` |
## Access transformers

Not a mixin and not counted in the budget. `META-INF/accesstransformer.cfg` makes `Entity.setSharedFlag(int, boolean)` and `getSharedFlag(int)` public, so the species part's `client/HunterSenseClient` can outline entities on one client (see docs/parts/species.md, Hunters: instinct, sense).
