# Mixins

Every mixin must be listed here. Budget: at most 3 per part, each `require = 0`, gated by that part's switch.

Convention: one mixin config and one `IMixinConfigPlugin` per part. The config is `supernaturalbloodlines.<part_key>.mixins.json` (the part key in snake_case), the plugin is `<Part>MixinPlugin` in `net.ofatech.supernaturalbloodlines.mixin`, and the mixin classes live in `mixin.<part>` (no separator, like the part package). The plugin applies the config only when all of `Part.requiredMods()` are installed and the part's switch is on (read through `EarlySwitches`, from the toml file, because COMMON configs load after mixins). Otherwise nothing is touched.

## species_tensura (2 of 3)

Config `supernaturalbloodlines.species_tensura.mixins.json`, plugin `SpeciesTensuraMixinPlugin`, package `mixin.speciestensura`. Applies only when Vampirism, Enchanted and Tensura are installed and the species and species_tensura switches are on (the plugin uses the same `PartLoader` rule as the part itself, so a part whose required part is off gets no mixins). The plugin logs one line saying whether they were applied.

| Part | Mixin | Target | Why | Config switch |
|---|---|---|---|---|
| species_tensura | `RaceUtilsMixin` | `RaceUtils.isUndead(Entity)` and `RaceUtils.isAffectedByHolyExposure(Entity)` in Tensura (HEAD, returns true), and `RaceUtils.isBloodless(Entity)` (HEAD, returns false for a race in `supernaturalbloodlines:bitable`: the apex races, plan 10) | R100: a species whose layer says `treatAsUndead` (and a plain Vampirism vampire) counts as undead for Tensura: holy and light damage x3 (`DamagingHandler`), holy exposure, infection and so on. The undead and holy-exposure methods are plain static checks with no event, no gamerule and no config (verified with javap, docs/parts/species_tensura.md). The `isBloodless` injection (plan 10) is separate: Tensura's `no_blood` race tag includes `#tensura:undead`, so the undead apex races would be bloodless to Tensura's Drain, Blood Mist and VampireRace feeding; for a `LivingEntity` whose race is in our `bitable` tag it returns false at HEAD (no switch of its own, and it does not depend on `UndeadTreatment`). The plugin checks all three hooks together (`raceUtilsHooked`). Only a `Player` is affected, and only when `UndeadTreatment.applies` says so. If Tensura renames the methods the injection is skipped (`require = 0`) and the layers keep granting skills and bonuses. **13d:** with `undead_treatment_enabled = false` the first two answer false for our apex races too (they sit in `tensura:undead` through a data file, and tags cannot carry load conditions in this NeoForge: checked). | `undead_treatment_enabled` in `supernaturalbloodlines-species_tensura.toml` (the mixin stays applied, the check returns to Tensura's own answer)
| species_tensura | `RaceInstanceMixin` | `ManasRaceInstance.getNextEvolutions(LivingEntity)` in ManasCore (`@At("RETURN")`, `cancellable`, `require = 0`) | R100: the one common-code place that the evolution screen's list, "set tracked" and the server's `contains` check all call, so adding the species' apex race to the (immutable) list makes it pickable and valid server side (`ApexOffer`). Its second injection, on `getEvolutionProgress` (the old x1.25 progress boost), was **removed in plan 10**: the boost now speeds up EP gain only, through Tensura's `AURA_GAIN`/`MAGICULE_GAIN` attributes (`EvolutionBoost`, no event, no mixin). The class stays because the apex offer still needs it, so species_tensura has 2 mixins (the Rite of Severance clearing the Tensura name needs none: `IExistence.setName(null)`; budget stays 2 of 3) (`RaceUtilsMixin`, `RaceInstanceMixin`). The plugin looks for the call in `postApply` and logs `RaceInstanceMixin hook in place` or a warning; the part logs a warning at init when the apex hook is missing. | `apex_evolutions_enabled` (apex offer) in `supernaturalbloodlines-species_tensura.toml` |

## hud (2 of 3)

Config `supernaturalbloodlines.hud.mixins.json`, plugin `HudMixinPlugin`, package `mixin.hud`. **Two mixins used:** `VampireRaceFeedMixin` (13c Task 2, below the first) and `AbilityStorageNextPresetMixin` (13b Task 2). Tensura's server refuses a skill that is only in preset N+1 (ManasCore's `ACTIVATE_SKILL` handler in Tensura's `AbilityHandler` calls `isAbilityInActivePreset(slot, skill, mode)`, which only looks at the active preset; `TensuraPresetGameTests` was red without the mixin and is green with it, and no event or API would have changed that answer). `@Pseudo` with the string target `io.github.manasmods.tensura.storage.ability.AbilityStorage`, `require = 0`, at RETURN of the four `isAbilityInActivePreset` overloads, a `false` becomes `true` when the skill is in the next preset at that slot and mode (`parts/hud/tensura/NextPreset`). Switch `next_preset_active` (read when a check runs). Applied only with Tensura installed; `HudMixinPlugin.postApply` logs if fewer than 4 hooks landed. The other two stay reserved, each added only after its task shows that no event or API works, with `require = 0`, its own switch in `supernaturalbloodlines-hud.toml` (`[mixins]`, all `true`) and its own `@Pseudo`/string target; one map entry per mixin in the plugin (simple class name to mod ids).

## supernatural (1 of 3)
Config `supernaturalbloodlines.supernatural.mixins.json`, plugin `SupernaturalMixinPlugin`, package `mixin.supernatural`. Applies only when Vampirism and Enchanted are installed and `parts.supernatural` is not `false` (the mixin targets Enchanted's `Rite`, the part itself only needs Vampirism). The plugin logs one line saying whether the mixin was applied and, in `postApply`, whether both hooks landed (`RiteCompleteMixin hook in place` or a warning).
| Part | Mixin | Target | Why | Config switch |
|---|---|---|---|---|
| supernatural | `RiteCompleteMixin` | `Rite.start()` (`@Inject` at the `INVOKE` of `stop()`, `require = 0`) and `Rite.cancel()` (HEAD, marks the instance in a `@Unique` field) | Enchanted 4.2.7 fires no event when a rite works (checked with javap: its `*Events` classes are client, common, effects and poppets). `start()` calls `stop()` only when `onStart` returned false, which means the rite is finished; a rite that refuses (`return cancel()`) ends the same way, so `cancel()` marks the instance and the signal is sent only for an instance that was not cancelled. `RiteSignal` then fires `rite:<datapack rite id>:performer / :target` through `TaskSignals` for the caster and for the rite's target (its own target player, else the player on the circle's centre). It is the single "a rite worked" signal for every rite, Enchanted's own types and ours (our rite factories no longer fire anything). A rite that keeps running (`onStart` true) and ends in `tick()` is not signalled: none of the rites the ladders ask for runs over time. Verified with real rites in `RiteSignalGameTests`: an Enchanted `create_item` type counts once, a rite of ours counts once, a cancelled rite counts for nothing. | `rite_complete_signal` in `supernaturalbloodlines-supernatural.toml` (the mixin stays applied, the signal is not sent) |

## celestials (0 of 3)

No mixin. The Blue Moon rite cost is one more factor in the species part's existing RiteCostMixin hook (RiteCost.begin), the Blood Moon bite bonus is a Vampirism event listener, the Super Blue Moon spare is a predicate in ForcedShift, and Enhanced Celestials 2 itself is read by reflection (EcReflect), so none of it needs a mixin. ## Access transformers

Not a mixin and not counted in the budget. `META-INF/accesstransformer.cfg` makes `Entity.setSharedFlag(int, boolean)` and `getSharedFlag(int)` public, so the species part's `client/HunterSenseClient` can outline entities on one client (see docs/parts/species.md, Hunters: instinct, sense).

**hud: renames.** The two `@Shadow` fields of `AbilityStorageNextPresetMixin` (`activePreset`, `presets`) are not covered by `require = 0`: a Tensura update that renames them makes this mixin config fail to apply (the game logs it and runs on, without the right column working), it does not crash. Every injector in `supernaturalbloodlines.hud.mixins.json` (the four next-preset hooks and the three of `VampireRaceFeedMixin`) is `require = 0`, and `HudMixinPlugin.postApply` logs whether each hook landed. **The next-preset mixin applies to every player on the server** (next-preset skills count as equipped, 6 instead of 3); `next_preset_active = false` in `config/supernaturalbloodlines-hud.toml` (`[mixins]`, a COMMON config) turns it off, and `tensura_feed_fills_blood = false` there does the same for the race feed.
Plan 17a (original lines) adds no mixin.


## Dev tooling (not a part, not counted in the budget)

Config `supernaturalbloodlines.devshots.mixins.json`, plugin `DevShotsMixinPlugin`, package `mixin.dev`. `DevShotsWindowMixin` is applied **only** when the JVM has `-Dsupernaturalbloodlines.devshots.hidden=true`; the plugin answers `false` otherwise, so a normal run and a release jar (which carries the config, never the property) apply nothing. It is client only. Exception to the `require = 0` rule on purpose: it is `require = 1`, because with the property on a missed hook must stop the start, not show a window.

| Mixin | Target | Why |
|---|---|---|
| `DevShotsWindowMixin` | `Window.<init>`, `@Inject` at the `INVOKE` of `net.neoforged.fml.loading.ImmediateWindowHandler.setupMinecraftWindow(IntSupplier, IntSupplier, Supplier, LongSupplier)J` (verified with javap on NeoForge 21.1.265 / FML 4.0.45) | Sets `GLFW_VISIBLE`, `FOCUSED`, `FOCUS_ON_SHOW`, `DECORATED` to false right before the window is made. In 1.21.1 `Window.<init>` has no `glfwCreateWindow` call: with `earlyWindowControl=false` the call is inside NeoForge's `NoVizFallback`, which creates the window with the hints that are set at that moment. With `earlyWindowControl=true` FML's early window already exists and visible, so `runSafeShots` writes `earlyWindowControl = false` into `run-safeshots/config/fml.toml` only. |
