# Part: species_tensura

Requires: `vampirism`, `enchanted`, `tensura`, and the `species` part active. Package: `net.ofatech.supernaturalbloodlines.parts.speciestensura`. Plan: `docs/superpowers/plans/05-species-tensura.md`.

Checklist (from the design, sections 5 and 10). Tick items as they ship.

- [x] Tensura races are never replaced: species are a layer on top of the player's race (SPECIES-RULES R3, R20, R100). The layer never calls `setRace`.
- [x] Species layer grants Tensura skills, attributes and an EP bonus; counts as undead where it matters (Task 2).
- [x] One apex evolution per species, unlocked for human-like races in Tensura's evolution screen (Task 3).
- [x] Intrinsic skills from Tensura's existing ones (layer skills: `blood_mist`, `drain`, `beast_transformation`, `self_regeneration`, `godwolf_sense`, `charm`; apex signature skills below); final lists chosen by the builder.
- [ ] Sync both ways with the unified vampire; the species layer wins over the plain vampire mapping.
- [x] Sireline link: `IExistence.setPermanentOwner(sireUUID)` when a sire is recorded; removed when the sire bond breaks (Task 4).
- [x] A sire can name their sired through Tensura's naming (R101) (Task 4).
- [x] Rank skills for werewolf packs (ALPHA → `beast_transformation`, `godwolf_sense`; TRUE_ALPHA adds the commander skill; born lineage → `godwolf_sense` at level 5); only skills this mod granted are removed.

### How the evolution screen builds its options (this is where apex races hook in)

1. Client: `EvolutionScreen` calls `ManasRaceInstance.getNextEvolutions(player)` (which is `getRace().getNextEvolutions(this, entity)`) for the list, and, per option, `TensuraRace.getEvolutionRequirements(inst, entity)` / `EvolutionRequirement.getProgress(inst, entity)` / `getRequirementComponent(inst, entity)` for the bars. The "tracked" evolution is `ITensuraPlayer.getTrackedEvolution()/setTrackedEvolution(ManasRace)`.
2. Client -> server: `RequestEvolutionPacket` (`tensura:request_evolution`, record `(Action, ResourceLocation, boolean)`, actions evolve / set tracked / awakening). The server handler `handleEvolution` checks `instance.getNextEvolutions(player).contains(target)`, then `getEvolutionProgress(player, target) >= 100.0f`, then `RaceHelper.evolveRace(player, target, bool)`. Setting the tracked evolution checks `getNextEvolutions(...).contains` too. ManasCore has its own `RequestRaceEvolutionPacket` with the same two checks and `Races.evolveRace(ManasRace)`.
3. So **one hook covers client list, tracking, and server validation: `ManasRaceInstance.getNextEvolutions(LivingEntity)`** (RETURN, add the apex race). It is common code (client and server) and both packets call it. Because it is the instance method that delegates to `ManasRace.getNextEvolutions(inst, entity)`, a mixin on the instance method needs one injection and does not depend on each Tensura race class. Both the list and `contains` see the apex race, so no second hook is needed. The mixin must return a mutable copy (`List.of(...)` in the races is immutable).
4. `RaceHelper.evolveRace(LivingEntity, ManasRace, boolean, boolean)` is the real change (`evolveRace(entity)` / `(entity, bool)` pick the default evolution). It ends in `Races.evolveRace` -> `setRace`, so `RaceEvents.SET_RACE` fires and vampirism_tensura's sync and `FactionRaceRules` see the new race.
5. Progress and requirements belong to the **current** race: `TensuraRace.getEvolutionProgress(inst, entity, target)` iterates `getEvolutionRequirements(inst, entity)` (a `Map<EvolutionRequirement, Float>` of requirement -> weight) and sums weight x `getProgress(inst, entity)`. Default for a `TensuraRace` is `Map.of(new EPRequirement(d), 1.0f)`. The requirement classes (`race.template.EvolutionRequirement` and nested): `EPRequirement(double ep)`, `AbilityRequirement`, `AwakenRequirement`, `BossRequirement`, `ItemCarryingRequirement`, `ItemConsumeRequirement`, `NamedRequirement`, `PhysicalBodyRequirement`. Progress is read live from the player's state (EP from `IExistence`, etc.), nothing is counted over time. `EvolutionRequirement` is a plain class with `getProgress(inst, entity): float` and `getRequirementComponent(inst, entity): Component`, so the "species bonus to the evolution requirements" (R100) can be done by wrapping a requirement or by a lower `EPRequirement`, per race, not through an event.
6. No Architectury or NeoForge event for "evolution options" exists (`RaceEvents` has only `POST_INIT`, `SET_RACE`, ticks, cooldown, ability activate/release). `SET_RACE` is the only event and fires before the change.

**Holy damage vs undead (what stacks).** `DamagingHandler`'s hurt handler (a ManasCore hurt event, `Changeable<Float>` amount) does `if (TensuraDamageHelper.isUndeadPurifying(source) && RaceUtils.isUndead(target)) amount *= 3.0f`. `isUndeadPurifying` = `isLightDamage(source) || isHoly(source)`. So a player the layer makes "undead" takes **x3** from Tensura holy and light damage by Tensura's own code. vampirism_tensura's `HolyDamageBridge` multiplies Tensura holy damage by `tensura_holy_vs_vampire` (default 1.5) for faction vampires on `LivingIncomingDamageEvent`. Both would stack to x4.5, so `HolyDamageBridge` skips a player whose layer treats them as undead (the plain Vampirism vampire layer does; so a faction vampire without a species also takes x3 and not x4.5). The bridge still applies when the species part is off or the undead treatment is switched off in config.

## Species layer (Task 2)

Code: `parts/speciestensura` (`SpeciesLayer`, `LayerSpec`, `LayerTable`, `UndeadTreatment`, `TensuraHumanLikeCheck`, `HumanLikeLine`, `TensuraSupernatural`, `SpeciesTensuraConfig`), the mixin `mixin/speciestensura/RaceUtilsMixin` (listed in `docs/mixins.md`) and the shared seam `shared/tensura/LayerQuery`.

- **Config** `config/supernaturalbloodlines-species_tensura.toml`: `layers` (list of `SPECIES=skill,skill|maxMagiculeBonus|maxAuraBonus|treatAsUndead`, key = a species name or `VAMPIRE` for a plain Vampirism vampire; an entry replaces the default of its key, a bad one is ignored with one warning) and `undead_treatment_enabled`. Defaults are the design table; all seven skill ids were verified in Tensura 2.0.1.5, none dropped.
- **When it runs** (`SpeciesLayer.sync`, idempotent): on every `BloodlineAccess` listener change, on login and respawn, on Vampirism `FactionLevelChanged` (the plain vampire layer), and every 200 ticks (a Tensura evolution may rewrite modifiers or skills; the tick pass is the safety net, the evolution itself does not touch the layer, pinned by `layerSurvivesTensuraEvolution`).
- **Skills**: the missing ones are learned with Tensura's `NoMagiculeCost` switch and tracked in `BloodlineState.layerSkills` (new field, codec `layer_skills`, default empty, merged in with a second map codec because a `RecordCodecBuilder` group holds at most 16 fields; a change of it alone does not notify the bloodline listeners). A skill the player already had is neither granted nor tracked, so it is never removed (`preexistingSkillKept`). Only tracked skills are forgotten, when they leave the layer (`curedLayerRemovesOnlyGrantedSkills`). - **Attributes**: `supernaturalbloodlines:layer_magicule` / `layer_aura`, `ADD_MULTIPLIED_BASE` by the fraction, on `TensuraAttributes.MAX_MAGICULE` / `MAX_AURA`. Both ids are in `StalePartModifiers` under `SPECIES_TENSURA`; its attribute filter now also covers the `tensura` namespace (it only looked at `minecraft` before).
- **Undead**: `RaceUtilsMixin` makes `RaceUtils.isUndead` and `isAffectedByHolyExposure` true for a player whose layer says undead (switch `undead_treatment_enabled`). Effect measured by `vampireLayerTakesTensuraHolyDamage`: a layered Original loses exactly 3x the holy damage of a control.

  - R103 (`ApexRule`): `FactionRaceRules` no longer denies the werewolf join or ejects a hunter only when the race is an **apex race of ours** (race id namespace `supernaturalbloodlines`; the id the player has, or is about to get) **and** the species is vampire-type (ORIGINAL, ORIGINAL_HYBRID, HYBRID, HERETIC, TRIBRID).   - Its two old tests run the old case through `LayerQuery.runWithoutLayer` (it silences only the two `LayerQuery` answers, not the `RaceUtils` mixin).

## Apex races and the evolution bonus (Task 3)

| Species | Apex race (`supernaturalbloodlines:`) | Signature skill (placeholder) | Undead tag |
|---|---|---|---|
| ORIGINAL | `primordial_vampire` | `infinite_regeneration` | yes |
| ORIGINAL_HYBRID | `primordial_hybrid` | `ultraspeed_regeneration` | yes |
| HYBRID | `moonblood_hybrid` | `godwolf_sense` | yes |
| WITCH | `ancestral_witch` | `magic_sense` | no |
| SIPHONER, HERETIC | `void_siphon` | `gluttony` | no (a heretic is undead through its layer, a siphoner is not) |
| TRIBRID | `tribrid_ascendant` | `ultra_instinct` | yes |
| HUNTER_OF_THE_FIVE | `eternal_hunter` | `danger_sense` | no |

- **Registration.** One class, `ApexRace extends TensuraRace` (not `DefaultRace`: that one needs a Tensura `RaceConfig`), configured by an `ApexSpec` (max health, attack and movement speed as `ADD_VALUE` modifiers, all placeholders; energy range and the 2,000,000 EP requirement (plan 10) are constants in `ApexRace`). Added with `RaceAPI.getRaceRegistry().register(id, supplier)` from the mod constructor, the same registrar Tensura's `TensuraRaces` uses. `ManasRace.equals` compares class and registry name, so the server's `getNextEvolutions(...).contains(target)` works with the seven ids.
- **Offer.** `ApexOffer.withApex` adds the apex race at the end of `ManasRaceInstance.getNextEvolutions` when the config allows it, the player's race is in `HumanLikeLine.SAINT_OR_HIGHER` and the species has an apex race. The result is a new `ArrayList` (Tensura's lists are immutable). Failures are caught: one warning, no apex option. The hook covers the client list, "set tracked" and the server packet; `apexEvolutionRunsThroughTensurasPacketHandler` presses Tensura's real `RequestEvolutionPacket` handler.
- **Progress** toward an apex race is Tensura's own: `TensuraRace.getEvolutionProgress` sums the weighted requirements of the **target** race (`ApexRace.getEvolutionRequirements` = one `EPRequirement`, 2,000,000), not of the current one, and `RequestEvolutionPacket` needs `>= 100`.
- **Evolution bonus (R100, plan 10): EP gain only.** A player with a species whose layer is not empty is credited `evolution_progress_multiplier` (default 1.25, range 1 to 10) times the EP Tensura gives them. **The hook is Tensura's own gain attributes, not an event.** Tensura has no EP-gain event (`TensuraEntityEvents` has `ENERGY_DRAIN_EVENT` and `ATTRIBUTE_BASE_CHANGE_EVENT`, and neither can change a gain), but `DeathHandler.gainEPEntity(gainer, victim, ep)` computes `ep * getAttributeValue(AURA_GAIN) / 100 * alignment` and adds it to the base `MAX_AURA` (the same with `MAGICULE_GAIN` for `MAX_MAGICULE`), capped per kill by the `MAX_AP_GAIN`/`MAX_MP_GAIN` game rules. Tensura's Gourmand skill uses the same attributes. So `EvolutionBoost.sync` keeps one permanent `ADD_MULTIPLIED_TOTAL` modifier `supernaturalbloodlines:ep_boost` of `multiplier - 1` on both, called from `SpeciesLayer.sync` (species change, login, respawn, faction change, every 200 ticks); `EvolutionBoost.boostedEp(player, gain)` is the one place that says what the factor is (the modifier amount is `boostedEp(p, 1) - 1`). The id is in `StalePartModifiers`, so it is stripped on login when the part is off. **The evolution progress and its requirements are Tensura's own** (`boostNoLongerRaisesEvolutionProgress`): nothing can be skipped. `evolution_progress_multiplier = 1.0` turns the bonus off (the key keeps its old name so existing configs keep their value). It is server-side now: the clients need no equal value. `boostAddsQuarterEpForSpeciesPlayers` calls Tensura's real `gainEPEntity` for a species player and a control. A player who had the old progress bonus loses it with the update; EP already gained is kept.
- **Hook missing.** The mixin plugin looks in `postApply` for our call in `getNextEvolutions` (`require = 0` would skip a renamed one silently), logs `RaceInstanceMixin hook in place` or a warning, and `SpeciesTensuraPart` warns once at init when the offer hook is absent. The switch `apex_evolutions_enabled=false` is the same state for a test (`apexHookMissingIsHarmless`): no apex option, Tensura's own list unchanged, the layers keep working.
- **Species lost after the apex race.** The race stays. The layer skills (species-only) are not part of the apex race's intrinsic list: the layer grants and tracks them, so they leave through `SkillOwners.release` when the species goes and come back when it returns (`apexKeptWhenSpeciesLost`). The signature skill is the race's own intrinsic skill and stays: only the species-only skills go dormant. **Mastery of a dormant layer skill is lost** (the skill is forgotten and learned fresh): saving it would need a new per-skill map in `BloodlineState` (its codec is at the 16-field cap), so it is documented, not built. It is the same loss as a cure.
- **Tags.** `human_like` holds all seven. `undead` holds the four vampire-type ones (not `void_siphon`: a siphoner is not undead; a heretic is, through the `layers` entry, not through the race). Tensura's `no_blood` includes `#tensura:undead`, so those four carry Tensura's `no_blood` tag, but `RaceUtilsMixin` answers `RaceUtils.isBloodless` false for them (the plan 10 review round; `apexRaceNotBloodlessToTensura`), so Tensura's drain, blood mist and VampireRace feeding reach them too. **But all seven are in our race tag `supernaturalbloodlines:bitable`** (`data/supernaturalbloodlines/tags/manascore_race/races/bitable.json`, read by `RaceTags.isBitable`), and every bloodless check of this mod skips it, so vampirism_tensura's bite refusal (`VampirePlayerBiteMixin` through `FactionRaceRules.isBloodless`) and the bloodless part of the werewolf-join check treat them as having blood. They stay `tensura:undead`: holy damage ×3 and the other undead rules are unchanged. Pinned by `apexRaceIsBitableButUndead` (a real bite on each vampire-type apex race) and `everyApexRaceIsRegisteredAndTagged`. The mod's only readers of `tensura:no_blood` are the two in `FactionRaceRules`.
- **R103.** `FactionRaceRules` now exempts an apex vampire-type race from the hunter **join** denial too (it only skipped the werewolf join and the hunter ejection before): `ApexFactionGameTests.apexRaceKeepsAnOriginalInTheHuntersButNotAPlainPlayer`.
- **A saved race that is no longer registered.** ManasCore does **not** fall back: `RaceStorage.load` -> `ManasRaceInstance.fromNBT` throws `NullPointerException("No race found for location ...")` inside `Entity.load`, so that player cannot load at all (`manasCoreThrowsForAnUnregisteredSavedRace`). A login reset would run too late, so the fix is the other way round: when Tensura is installed and `species_tensura` is off, the mod constructor still registers the seven apex races (`ApexRaces.register()`, log line `Apex races registered without species_tensura`). They then exist as plain races with no offer. Removing Tensura or this mod is not covered: the same load fails for every Tensura race.
- **R103 matches by namespace.** `ApexRule.isApexVampire` checks the race id's namespace (`supernaturalbloodlines`), not the `ApexSpec` list: any race registered under that namespace is exempt for a vampire-type species. Only this part registers there.
- **Part off.** With `species_tensura` off the apex races stay registered (so saved players load) but `LayerQuery` answers false, so R103 has no exemption: an Original hunter on `primordial_vampire` is ejected from the hunters when the race is set, and may not rejoin.
- **Removing the mod.** Reset apex-race players with Tensura's race command before removing the mod: a saved race that is not registered stops that player from loading (see above).
- **Not done / open for the owner.** Names, stats, EP requirement and signature skills are placeholders. No race icon texture (`icons/races/<id>`) exists, so the evolution screen will probably show a missing-texture icon (not checked in a client). `getPreviousEvolutions` of an apex race is empty (the evolution tree may not draw the link back).

## Sireline as Tensura subordinates, and naming (Task 4)

Code: `parts/speciestensura` (`SubordinateLink`, `SireNaming`), the mixin `mixin/speciestensura/SireNamingMixin` (third and last of the budget; listed in `docs/mixins.md`), tests `gametest/SirelineTensuraGameTests`. Config (`supernaturalbloodlines-species_tensura.toml`, common): `sire_subordinate_link_enabled` and `sire_naming_enabled`, both default on.

**The link (R101).** A sire becomes the child's `IExistence` permanent owner, which is what `SubordinateHelper` reads (owner order: temporary owner, summoner, permanent owner, then an `ISubordinate`'s own owner).
- Player child: `SubordinateLink.sync` runs on every `BloodlineAccess` change (species, sire and so on), on login and on a Vampirism faction change. The owner is set when the player has a sire **and is still supernatural** (`Supernatural.is`: a species, a vampire or werewolf, a Tensura undead or daemon race). A player who loses the species but keeps a stale sire loses the link, and gets it back with the species (`speciesLossEndsLinkAndRegainRestoresIt`). A cure or any other sire change clears the owner, but only while it is still that sire (`cureRemovesSubordinateLink`).
- A Tensura owner the child already has is never overwritten (logged once, the sire is still recorded; `existingTensuraOwnerKept`). Because the owner is then not the sire, the naming lift does not apply either: Tensura's `had_owner` refuses the sire.
- Creature child: `SireRecorder`'s listener sets the owner; an `ISubordinate` creature with an online sire is also `tame`d by it. An offline sire gets the owner only (no tame, no later retry). The creature's link is never cleared (it is removed from the index when it dies or is cured, and the entity itself is replaced).
- **What is ours to remove.** The sire the link made the owner is also stored in the child's persistent data (`supernaturalbloodlines:linked_sire`; copied over a death). `sync` unlinks when the player has no sire, is not supernatural, or `sire_subordinate_link_enabled` is off, and it clears Tensura's owner only while that still equals the stored sire. An owner Tensura set itself (a naming makes the sire the owner too, with no stored sire) or changed since is left alone (`switchOffUnlinksOnlyWhatWeLinked`).
- **Switch and part off.** The switch is read when a player logs in, their bloodline changes or their faction changes, so to remove the links: set `sire_subordinate_link_enabled = false` and have everyone log in once, **then** disable the part. With the part off nothing runs, so existing links (and the one-way friendly fire) stay until the owner is cleared by hand (`/tensura` owner commands) or the part is on again.

**What being a Tensura subordinate means for a player** (bytecode of `DamagingHandler`, `MixinEntity`, `MixinLivingEntity`, `ExistenceStorage`, `DeathHandler`):
- **Friendly fire is one way.** Tensura's hurt handler cancels damage from a subordinate to its owner and between two subordinates of the same owner. The owner can still hurt the subordinate. So a sired player cannot hurt their sire (or the sire's other sired) with a hit that goes through that handler. This applies to werewolf bites too: a bitten player's sire is the Alpha. It is the largest side effect; `sire_subordinate_link_enabled = false` removes it. (Found by `HybridTraitsGameTests.sireProtectedFromIndirectDamage`, which expects a cured hybrid with a stale sire to hurt the sire: hence the supernatural condition above.)
- Owner and subordinate count as allied (`Entity.isAlliedTo` mixin), and a creature never targets its owner (`canAttack`).
- A demon lord sire's harvest festival hands its subordinates a gift, which can evolve them through Tensura's own rules; a subordinate's kills give soul points to a player owner only with the `hardcoreRace` rule and a demon lord seed (so `siredMobKillCreditsSire` pins the owner lookup those paths use, not an EP transfer: Tensura gives the killer's EP to the killer, not the owner).
- No Tensura command or skill makes a subordinate player obey. Owner-only skills that read the owner (Commander, Spearhead and others) see the sired as the sire's subordinate, as they would for a named one.

**Naming.**
- One wrap in `RequestNamingKeyPacket.isNotNameable` (see the `canName` rows above). `canName` itself needs no change: once the sire owns the sired, the sire passes `isSubordinate`, `had_owner` and `isNotSubmitting` (a subordinate always "submits"). `RequestNamingMenuPacket.name` calls `canName` again, so one wrap covers key and menu.
- Lifted only for the pair `SirelineIndex.sireOf(target) == namer` while the target has no Tensura name. A stranger, another sire and the sire naming a non-sired player are refused (`sireCanNameOwnSiredOnly`, `nonSireCannotNameWithGameRuleOff`).
- **The sired's own nameable toggle is respected.** Tensura's players are not nameable by default (the field defaults to false; the player toggles it by sneaking with the naming key), and that consent also stops a sire from giving a player a custom display name. So a sire can name a sired player who switched naming on, with the server rule off. The rule only goes away for the sire.
- Costs and rewards are Tensura's. `namingReward` raises the target's base max magicule and aura for every type, then, for MEDIUM and HIGH, runs `getHarvestFestivalEvolution` and `RaceHelper.evolveRace` on **any** target, a player included (`evolveMobs` is the non-player part; HIGH also adds skill learn points). Measured: a plain human named HIGH becomes `enlightened_human`. A sired player must not be evolved by their sire (R100), so `SireNaming` registers on `NAMING_EVENT` and lowers the type to LOW for a player the namer sired: stats, no evolution, no learn points (`namingSiredPlayerDoesNotChangeRace`, with the control above and a mutation check). The magicule cost is computed before the event, so the sire pays for the type they chose. **The loss of the namer's max magicule is kept**: Tensura rolls it from the type that is final after the event (`shouldConsumeMax`: HIGH `endowLostChance` 50, MEDIUM `evolveLostChance` 20, LOW `subdueLostChance` 0), so lowering the type would have dropped it. `SireNaming` rolls the chosen type's chance itself and applies Tensura's effect (base max magicule down by the cost; with the default alignment the cost is paid from current magicule first and the rest comes off max aura; skipped for a creative namer); Tensura's own LOW roll still follows and only matters if `subdueLostChance` is raised (`namingSiredPlayerKeepsTheNamersMaxLoss`, chance 100 and 0 set through `NamingMenu.CONFIG`). Creatures keep the full reward.
- The sire/sired pair also needs the sired to be supernatural (a cured player with a stale sire in the index is a stranger).
- The part warns at init when the wrap is not in place (`SireNaming.hookApplied`); the link keeps working. The flag is set by `SpeciesTensuraMixinPlugin.postApply` like the other two hooks, but MixinExtras rewrites a `@WrapOperation` call site only after `postApply` and a handler with `@Local` is wrapped in a `SugarWrapper`, so the plugin cannot see our handler's call in `isNotNameable`. It checks the other half: the call named by the handler's own `@At(target = ...)` (`GameRules.getBoolean`) is in `isNotNameable`. Verified by mutation: pointing the `@At` at a missing method gives the `SireNamingMixin hook MISSING` warning and fails `sireCanNameOwnSiredOnly`.

**Owner point: Tensura unique skills on a sired player** (javap of `StarvedSkill`, `UsurperSkill`, `GluttonySkill`; read from bytecode, not played). None of them tests for a subordinate, so the link neither protects nor exposes a sired player more than any other player:
- **Starved** (held corrosion, radius): hurts entities near the user, plunders their skills as temporary skills (`SKILL_PLUNDER` event; entities tagged `no_skill_plunder` are skipped) and drains their max EP (`drainEnergy` MAX_EP) for the user's gain.
- **Usurper**: touch drains magicule; pressed it can rob a random skill (learned by the user, forgotten by the target: a real removal) or copy one, and the takeover mode makes the user the target's temporary owner (`setTemporaryOwner`), which Tensura reads before the permanent owner, so a takeover masks the sire for its duration.
- **Gluttony**: predation mist damage and corrosion; no skill or EP transfer from players found.
- A sire with Starved or Usurper can use them on a sired player (the one-way friendly fire only stops the sired hitting the sire). The skills this mod grants are not special-cased, so a robbed layer skill is simply re-granted by the next `SpeciesLayer.sync`. Nothing was changed for this; it is the owner's call whether sireline members should be exempt.

**`/bloodline call` follow through `SubordinateHelper` (plan 08, deferred): not done.** `CallFollowers` already walks sired creatures to the caller, and a tamed `ISubordinate` creature follows its owner with Tensura's own AI. Tensura's `setFollow` would need a hook in `shared` (species must not import Tensura), for no new behaviour.

**Not done / open.** An offline sire's `ISubordinate` creature is not tamed later. No message tells the sire that a sired player's naming has no evolution.

## Werewolf rank skills

Code: `parts/speciestensura` (`RankSkills`, `RankSkillTable`), tests `gametest/RankSkillsGameTests` (registered only when Werewolves is loaded) and `RankSkillTableTest`. `RankSkills` is registered only when Werewolves is loaded; it links no Werewolves class (the faction is matched by id `werewolves:werewolf`).

- **Config** (`supernaturalbloodlines-species_tensura.toml`, `rank_skills`): `"RANK=skill,skill"` with RANK `ALPHA`, `TRUE_ALPHA` or `BORN_LEVEL5`. Defaults: `ALPHA=tensura:beast_transformation,tensura:godwolf_sense`, `TRUE_ALPHA=` the Alpha skills + `tensura:commander`, `BORN_LEVEL5=tensura:godwolf_sense`. An entry replaces the default of its key; a bad entry (unknown RANK, bad skill id) is ignored with one warning and the default stays.
- **When it runs** (`RankSkills.sync`, idempotent): on every `BloodlineAccess` listener change (so on a change of `wolf.rank` or `wolf.lineage`), on Vampirism `FactionLevelChanged` (the werewolf level), on login and respawn, and every 200 ticks.
- **What is wanted**: the skills of the player's rank (`ALPHA`, `TRUE_ALPHA`), plus `BORN_LEVEL5` while `wolf.lineage == BORN` and the player is a werewolf of level 5 or more. The rank skills need the werewolf faction (plan 10 review: `wanted` is empty outside it): a cured True Alpha keeps the rank, dormant, and `SkillOwners.release` takes the skills back on leaving; the `FactionLevelChanged` listener re-grants them on rejoining (`dormantTrueAlphaSkillsReturnOnRejoin`). Omega and Beta have no entry. The skills never change the race (the Beastfolk line, R20b, does).
- **Tracking**: skills are granted free of magicule cost and tracked in `WolfState.grantedSkills` (`granted_skills`; a change of it alone does not notify the listeners). Only tracked skills are released, through `SkillOwners.release`, so a skill the layer (`godwolf_sense` and `beast_transformation` for an ORIGINAL_HYBRID) or the werewolf level grants still wants stays; the last source to let go forgets it. A skill the player had before is never tracked (`losingAlphaRemovesOnlyGrantedSkills`, `losingTheRankKeepsASkillTheLayerStillWants`). The source is registered with `SkillOwners` as `wolf_rank`.
- **Rollbacks**: `BloodlineAccess.restore` now also keeps the current `wolf.grantedSkills`, like `layerSkills`.
- **Mastery** of a released skill is lost, as for the layer.

## Operations notes (panel fixes)

- **Granted skills stay when the part is off.** The layer, rank and link code only runs while `species_tensura` is on. Skills it already granted (and `layerSkills` / `wolf.grantedSkills`), the sireline links and their one-way friendly fire stay on the player until the part is on again or they are removed by hand. To clean up first, remove the species from the players (or set `layers` / `rank_skills` to empty and let everyone log in), then switch the part off.
- **Rolling back to a build before this part:** first reset apex-race players with Tensura's race command; back up the world before the first deploy.
- **Bad `layers` / `rank_skills` entries** are logged at ERROR with the entry text when the config loads, and ops (permission level 2 or more) get one chat line on login (`supernaturalbloodlines.species_tensura.bad_config`). The default of the entry's key stays.
- **Naming rule (owner decision).** `sire_naming_enabled` bypasses Tensura's `playerNaming` game rule for a sire and their own sired only. The server's `playerNaming=false` does not beat it. A sire who names a sired player with MEDIUM or HIGH is told once that it grants EP and stats only, never an evolution (`supernaturalbloodlines.sire_naming.no_evolution`). Siring needs no consent (it comes from blood or an Alpha bite); a rite to break the link is planned separately.
- **Apex config mismatch (known gap).** If `apex_evolutions_enabled` is on for the client and off for the server, the client shows the apex race and the server silently refuses the pick. The refusal happens in Tensura's `RequestEvolutionPacket` handler, after `getNextEvolutions(...).contains`; our hook on `getNextEvolutions` cannot tell that call from any other query of the list, and a hook on the packet needs a fourth mixin (the part's budget is three), so nothing is logged. Keep the common config equal on both sides.
- **Tested Tensura build:** `2.0.1.5` (README). The tests and the bytecode facts in this file depend on it.
- **Mixin plugins** share one base, `mixin/PartMixinPlugin(Part)`; `SpeciesTensuraMixinPlugin` adds the `postApply` hook checks (`RaceUtilsMixin`, `RaceInstanceMixin` (one hook since plan 10), `SireNamingMixin`).
- **Rite of Severance (R101b, species part).** A sired player whose bond was broken counts like a player with no sire here: SubordinateLink reads BloodlineState.boundSire() (so it unlinks when the bond is severed and links again to a new sire), and SireNaming.isOwnSired is false. The recorded sire stays for the tree. The owner a real naming set (no link of ours stored) is cleared too (SubordinateLink.freeFrom), but only when it equals the severed sire: someone else's owner stays, and so does the name. Pinned by severanceFreesTheOwnerAndTheNaming and severanceClearsTheOwnerANamingSet.
