## Shared plumbing (Task 1)

- **Hooks into the rite factory.** `vampirismenchanted.rite.FactionRiteHooks` holds a `ContextProvider` (`(target, faction, gameTime) -> BloodlineContext`, default `defaults()` + faction + time) and an `OutcomeRunner` (default `FactionRiteFactory.runFactionActions`, leave then join). `FactionRiteFactory` calls them for the preview and for the real call with the same context, and never imports a species class. `SpeciesPart.init` installs `SpeciesContext.of(p, faction, time, null)` and `OutcomeExecutor.run`; with `species` off the defaults stay (plan 3 behaviour).
- `SpeciesContext.of(p, bloodSource)` / `.of(p, faction, gameTime, bloodSource)`: faction (`FactionRiteFactory.baseFaction`), `humanLike` (`SpeciesEligibility`), Originals count (`SpeciesData`), `max_originals_per_world`, `transition_ticks`, `werewolvesLoaded`. `fiveCount` comes from `FiveRoster`, `maxFive` from `max_five`.
- `SpeciesEligibility.setCheck(HumanLikeCheck)`: plan 5 installs the Tensura check (`tensura:human_like`); the default is "everyone".
- `SpeciesData` (`SavedData` `supernaturalbloodlines_species`, overworld storage): UUIDs of ORIGINAL and ORIGINAL_HYBRID players, kept by a `BloodlineAccess` listener (species changes only), so offline Originals count. It keeps Originals who no longer log in, so their count stays against `max_originals_per_world`.
- `SpeciesConfig` (own file `supernaturalbloodlines-species.toml`, section `species`): `max_originals_per_world` (0 = unlimited), `transition_ticks` (24000). The brief put the spec inside `SpeciesData`; it is a separate class like `VampireSyncConfig`.
- **No Werewolves.** `BloodlineContext.werewolvesLoaded` (default true, set by `SpeciesContext`): when false, `BloodlineRules.apply` refuses any result that becomes a hybrid type or starts the hybrid transition with `supernaturalbloodlines.refusal.needs_werewolves`. The rules stay pure; the check is one wrapper in `apply`, so the rite preview refuses before anything changes.
- `OutcomeExecutor.run(p, outcome)`, inside `ReentrancyGuard.run(uuid, "species", ...)`: a refusal is sent as a chat message; otherwise LEAVE/JOIN as the rite factory does, then KILL_PLAYER = `hurt(source(supernaturalbloodlines:failed_transition), Float.MAX_VALUE)`. The damage type is in `#minecraft:bypasses_resistance` and `#minecraft:bypasses_invulnerability` (Resistance V and a Totem of Undying cannot save the player); if the player is still alive afterwards the executor calls `p.kill()`. Creative and spectator players are skipped. **No nested executor for the same player:** the guard channel is `species` per player, so an `OutcomeExecutor.run` that starts while another one for the same player is running (for example from a faction event the first one caused) is dropped with a warning in the log; do the follow-up after the outer call returns, or from another channel. `SpeciesData` is also re-synced from the player's species on login (`SpeciesPart.syncOriginal`).

## Originals (Task 2)

- **Registries** (`SpeciesRegistries`, registered by `SpeciesPart.init`): item `original_blood` (own drinkable, `UseAnim.DRINK`, 32 ticks, gives back a glass bottle; blood without a source cannot be drunk), effect `original_blood` (6000 ticks, marker only), data component `blood_source` (UUID), attachments `blood_source` (UUID, last drink wins, not copied on death: read it while the player is still alive, e.g. in the death event) and `downed` (ticks left, saved). Task 3 reads `blood_source` + the effect for `DIED_WITH_ORIGINAL_BLOOD`.
- **White oak** (`item/WhiteOak`): log, planks, sapling (grows `worldgen/configured_feature/white_oak.json`, a vanilla-shaped oak with our log, via `TreeGrower`), `white_oak_stake` (wooden sword stats). The item tag `supernaturalbloodlines:white_oak` holds the stake; any main-hand item in it is "white oak". The sapling is craftable (oak sapling + amethyst shard) because nothing drops it. Placeholder textures, generated.
- **Rites**: `immortality.json` (`faction_rite`, event `rite_of_immortality`, `faction: none`, `requires_full_moon`, power 12000, items white oak sapling + golden apple + `vampirism:human_heart`, entity `minecraft:villager` consumed; the target is `RiteTargets.centrePlayerOrCaster`). `original_blood.json` (factory `supernaturalbloodlines:original_blood`, one glass bottle, power 1000): refuses a non-Original target with `supernaturalbloodlines.refusal.not_original` on the action bar and Enchanted gives the bottle back. Both are conditioned on `part_enabled species`.
- **Protection (R32)** (`original/OriginalRules`, `LivingDeathEvent` at HIGH with `receiveCanceled` (Vampirism's `onLivingDeathFirst` is HIGHEST, so we run right after it and before any NORMAL/HIGH handler of another mod); a `LivingDeathEvent` is used, not `LivingIncomingDamageEvent`, because only the death event knows the damage after armour): the exempt sources are white oak (direct attacker's main hand in the tag), `fell_out_of_world`, `generic_kill`, `#minecraft:bypasses_invulnerability` (holds `failed_transition`). Anything else lethal: a vampire Original is cancelled by Vampirism's own `onDeadlyHit` first (we see a cancelled event and leave it); otherwise (Original hybrid, or a vampire Vampirism does not down) we cancel and start `Downed`. A white oak blow on an Original already in Vampirism's dying state ends it by reflection (`VampirePlayer.giveUpDBNO()` is not in the API jar), then killed with a `generic_kill` source that names the attacker (kill credit), and Vampirism's state is reset after the kill. Vampirism blocks all damage to a player in its dying state, so a white oak blow on one is caught in `LivingIncomingDamageEvent` at HIGHEST.
- **`Downed`** (Original hybrids; Task 5 reuses it for werewolf-faction Originals): the `downed` attachment counts down from 600, movement speed and jump strength are locked by a transient `supernaturalbloodlines:downed` modifier (-100%), forced SLEEPING pose, attack/use/interact/break events are cancelled, non-exempt damage is cancelled (`LivingIncomingDamageEvent`), revive at half health after 600 ticks, `giveUp` kills with the source that downed them (kept in memory; after a relog it is a plain /kill source). The screen (`DownedScreen`, Give up / Wait) is opened by `DownedPayload(true)` and sends `DownedGiveUpPayload`; the class is only referenced from the payload handler lambda, so a dedicated server never loads it. Optional payload channel (version "1").
- **Attributes (R31)**: `OriginalRules.sync(player)`: +4 max health (add) and +20% attack damage (`ADD_MULTIPLIED_TOTAL`, so x1.2 of the final value, weapon included), saved (permanent) modifier id `supernaturalbloodlines:original` so health above 20 survives a relog, applied on a species change (BloodlineAccess listener), login, respawn and dimension change.
- **GameTest note**: `FakePlayer.die` is a no-op, so no `LivingDeathEvent` ever fires for a plain FakePlayer. Use `TestPlayers.createMortal` for tests that need the death event; `FakePlayer`s also never tick, so reset `invulnerableTime` between two hits.

## Hybrid transition (Task 3)

- **Where:** `parts/species/hybrid/TransitionHandler`, registered by `SpeciesPart.init` only when `werewolves` is loaded (it links no Werewolves class itself; the faction comes from `SpeciesContext`). The GameTests (`HybridGameTests`) link Werewolves and are registered only with it.
- **Death:** `LivingDeathEvent` at LOW (not receiving cancelled events) for a player with the `original_blood` effect: `DIED_WITH_ORIGINAL_BLOOD` with `bloodSource` = the `blood_source` attachment (last blood drunk wins). A `failed_transition` death is skipped, otherwise a timeout or unstable death would restart the transition. The state (`inTransition`, `pendingSire`, `transitionTicksLeft`) lives in the bloodline attachment, which is `copyOnDeath`, so the player respawns in the transition.
- **Timer:** `PlayerTickEvent.Post`, every 20 `tickCount` ticks `secondPassed` subtracts 20 from the saved `transitionTicksLeft` (online time only; a relog resumes it, a respawn only restarts the 20-tick phase). At 0: `TRANSITION_TIMEOUT` (the rules add `KILL_PLAYER`) through `OutcomeExecutor`.
- **Drinking:** `DoppelgangerBloodItem` (own drinkable, only usable in a stable transition; gives the bottle back) → `DRANK_DOPPELGANGER_BLOOD` (HYBRID, or TRIBRID for a witch, with `pendingSire` as sire). Other blood = an item in `#supernaturalbloodlines:blood_drinks` (Vampirism's `blood_bottle`, `required:false`) finished during a transition (`LivingEntityUseItemEvent.Finish`) → `DRANK_OTHER_BLOOD` → state `unstable` + the `unstable` effect (1200 ticks, not curable by milk). `secondPassed` kills when the state is unstable and the effect is gone (ran out or was removed): `UNSTABLE_DEATH`, then `KILL_PLAYER` through the executor (the rules' `UNSTABLE_DEATH` carries no kill action, the handler adds it).
- **Original's Blood during a transition is a second dose (R45) and changes nothing.** `BloodBottleItem.use()` returns PASS below vampire level 1, so a werewolf never starts the drink and `LivingEntityUseItemEvent.Finish` never fires for a Vampirism bottle (pinned by `vampirismBottleCannotBeStartedByAWerewolf`). So `TransitionHandler.onRightClick` (`PlayerInteractEvent.RightClickItem`) takes over the click for an item in `#blood_drinks` while `inTransition && !unstable`: it cancels with CONSUME and, on the server, uses up one item (not in creative), gives back a glass bottle and calls `drankOtherBlood`. The `Finish` listener stays for other tagged drinks. **Deferred: a bite as "other blood".** No Werewolves bite hook exists in the notes; add one when a hook is found. A death while unstable applies `UNSTABLE_DEATH` without a kill (they are already dying). The countdown is saved with `setData` and not synced each second; the client's copy of `transitionTicksLeft` is stale until the next real change or login.
- **Rite** `doppelganger_blood.json`: `enchanted:create_item` → Doppelgänger Blood, small circle, power 6000, items filled taglock + 2 diamonds + amethyst shard (the taglock is a plain ingredient, nothing is checked about whose it is), conditions `part_enabled species` and `mod_loaded werewolves`.

## Hybrid traits, thirst, venom, sire bond (Task 4)

All in `parts/species/hybrid/`, registered by `SpeciesPart.init` only behind `isLoaded("werewolves")` (the effect, item and rite factory are registered always; they link no Werewolves class). Only `FormControl` links Werewolves (`WerewolfFormAction`); everything else matches factions by id (`werewolves:werewolf`, `vampirism:vampire`).

- **`HybridTraits`**: for HYBRID, ORIGINAL_HYBRID and TRIBRID, a permanent modifier `supernaturalbloodlines:hybrid` (already in `StalePartModifiers`): +0.02 movement speed and +2 attack damage (`ADD_VALUE`) times `min(1, (gameTime - turnedAt) / 1_200_000)`; `turnedAt == 0` (unset) counts as fully grown. Applied on a species change (BloodlineAccess listener), login, respawn, dimension change, and recomputed every 1200 player ticks. Removed when the species is lost. `HybridTraits.register()` runs even without Werewolves, and `sync` only applies the traits when Werewolves is loaded, so a modifier saved earlier is stripped on login/species change/the 1200-tick recompute (pinned by `hybridTraitsFollowTheWerewolvesMod`, which runs with `-PnoWerewolves` too). `BloodThirst.refreshEffects` renews its 100-tick effects only when under 40 ticks remain (fewer packets).
- **`FormControl`** (hybrids shift at will; the detection moved to `shared.werewolves.ForcedShift` in the artifacts plan, and `FormControl` now only registers the hybrid types as a `MoonControl` source; the paragraph below describes what `ForcedShift` does): a listener on `ActionEvent.ActionActivatedEvent` cancels a `WerewolfFormAction` for a hybrid type only while that player is inside its own `PlayerTickEvent` (thread-local set in `Pre`, cleared in the last `Post`). That is the forced full-moon shift; a voluntary shift comes from a packet, outside the tick. No mixin. Plan 9's `MoonControl` can build on `FormControl`. Not decided here: R96 "once unbound" (`hybridCurseBound`) is plan 9's; the forced shift is cancelled for bound hybrids too.
- **`BloodThirst`** (`BloodlineState.thirst`, 0 to 20): a hybrid's right click on an item in `#blood_drinks` is taken over (a werewolf-faction player cannot start Vampirism's bottle), the bottle is used up (glass bottle back) and thirst rises by `GAIN` = 5, only below 20. Falls by 1 every 1200 player ticks. Weakness I at 0 and Strength I from 15 are short (100 ticks), ambient effects renewed every 20 ticks, so they fade by themselves. Only the thirst field changes, so the species listeners do not run; `BloodlineAccess.set` sends one sync when it changes. **Deferred: the Werewolves bite as a source of thirst** (no bite hook, as in Task 3).
- **`Venom`** + effect `hybrid_venom` (12000 ticks): a melee hit (direct entity = attacker, not thorns, damage dealt > 0) by someone in the werewolf faction (a player, or a Werewolves mob through `IFactionEntity`) on a vampire (a player in the vampire faction, or an `IVampire` mob) applies it, once (a second bite does not reset the timer). The effect pulses when `duration % 40 == 0` and on its last tick: 1 damage that never takes the last half-heart (`supernaturalbloodlines:venom`), Nausea II for 100 ticks when `duration % 600 == 0` (the hallucination; **plan 7 can swap in its `HallucinationPayload`** in `Venom.pulse`), Weakness II (60 ticks, renewed) and nothing else for an Original or Original hybrid (R42v: no tick damage, no hallucination). The last pulse kills a non-Original with `supernaturalbloodlines:venom` (in `bypasses_invulnerability`, `bypasses_resistance`, `bypasses_armor`, `bypasses_cooldown`, so a totem, Resistance and Vampirism's dying state do not save them; `kill()` as a fallback). Creative and spectator players are skipped. `fillEffectCures` is empty, so milk does not cure it.
- **Hybrid's Blood**: item `hybrid_blood` (drinkable only while poisoned; gives the glass bottle back; removes `hybrid_venom` with `removeEffect`, which ignores cures; not in `#blood_drinks`), rite `hybrid_blood.json` (factory `supernaturalbloodlines:hybrid_blood`, `HybridBloodRiteFactory`: refuses a non-hybrid target with `supernaturalbloodlines.refusal.not_hybrid`; one glass bottle, power 1000; conditions `part_enabled species` + `mod_loaded werewolves`). Original's Blood does not cure the venom (pinned).
- **`SireBond`**: `LivingIncomingDamageEvent` at HIGH cancels damage whose attacker or direct entity is, or is owned by (arrow/projectile owner, area effect cloud owner, tamed pet owner, up to 4 hops), a hybrid-type player whose `sire` is the victim's UUID. A cured player with a stale `sire` is not bound.
- **Sire bond gaps (known, accepted):** the bond follows owners (`getOwner()`), so damage from an `AreaEffectCloud` with no owner (a dispenser, or an owner whose entity is gone) is not cancelled, and neither are arrows whose owner is offline or unloaded (`getOwner()` is null). Plan 8 can store the owner UUID on the cloud/projectile if this matters.
- **GameTests**: `HybridTraitsGameTests`. `FakePlayer.canHarmPlayer` is always false, so player-versus-player damage needs `TestPlayers.createDuelist` and the server's PvP switched on while hitting (`hit()` in the tests).

## Original hybrid (Task 5)

- **Rite of the Moon** `rite_of_the_moon.json`: `faction_rite`, event `rite_of_the_moon`, faction `vampire_or_werewolf`, `requires_full_moon`, power 15000, medium circle, items `moonstone` + Original's Blood, consumed entities 1 wolf + 1 villager, conditions `part_enabled species` + `mod_loaded werewolves`. The rules decide (R35): an ORIGINAL with `wolf.latentGene` becomes ORIGINAL_HYBRID (unbound, BORN/OMEGA, leaves the vampires, joins the werewolves); without the gene `no_gene`; a bound hybrid of any hybrid type is unbound (R96), staying in the werewolf faction.
- **Moonstone** (`supernaturalbloodlines:moonstone`, placeholder texture): shapeless amethyst shard + `werewolves:silver_ingot`, gated on `werewolves`. **No loot source yet.**
- **Original hybrid in play:** hybrid traits (`hybrid` modifier) and Original protection (`original` modifier: +20% attack as `ADD_MULTIPLIED_TOTAL`, +4 max health) use different ids and operations, so they stack (attack = (base + faction + 2 * age) * 1.2). Lethal damage puts them in our `Downed` (no Vampirism dying state in the werewolf faction).
- **Rite of Lineage** is plan 9's. Here only the rule path is pinned: `RITE_OF_LINEAGE_AWAKEN` on an Original gives a bound ORIGINAL_HYBRID with the gene.
- **Gene kill (R24)** `hybrid/GeneAwakening`: `LivingDeathEvent` at LOW, not receiving cancelled events (so a downed or DBNO victim is no kill). The killer is a `ServerPlayer` with `wolf.latentGene` (the only pre-filter; `BloodlineRules` decides who qualifies), the victim a `Villager` (not a wandering trader) or a player: `GENE_AWAKENED_AS_VAMPIRE` through `BloodlineAccess.applyEvent` and `OutcomeExecutor`. A plain vampire becomes a bound HYBRID. Refusals (heretic) and no-ops (a human) are silent and run no actions.
- **Level carry-over:** when an outcome has `LEAVE_FACTION` and then `JOIN_WEREWOLF` from the vampire faction (R24, Rite of the Moon on an Original), `OutcomeExecutor` sets the werewolf level to `max(1, min(oldVampireLevel, werewolf highest reachable level))`; werewolf to vampire (Silver Moon on a hybrid) is `max(1, min(oldWerewolfLevel, vampire highest))`. The old level is read before leaving. `FactionRiteFactory.runFactionActions` (used alone when species is off) keeps its level 1. **Plan 9 rolls the gene**; nothing here does.
- **GameTests**: `OriginalHybridGameTests` (Werewolves only).

## Witch and siphoner (Task 6)

Package `parts/species/witch`; mixins in `mixin.species` (see [mixins](../mixins.md)).

- **Rite of Ancestral Calling** `ancestral_calling.json` (factory `supernaturalbloodlines:ancestral_calling`, `AncestralCallingRiteFactory`; small circle, power 4000, bone + amethyst shard + lapis lazuli, condition `part_enabled species`; no Werewolves needed). The player on the circle (else the caster) gets ANCESTRAL_CALLING_SIPHONER with the config chance `siphoner_chance` (default 0.25), else ANCESTRAL_CALLING_WITCH; the roll uses the level's random (`pick(RandomSource, chance)`; tests pin the chance with `SpeciesConfig.overrideSiphonerChance`). The rules refuse vampires, hunters and anyone with a species; the refusal goes to the caster's action bar.
- **Witch bonus** (`WitchAltarBonus`, config `witch_bonus_enabled`, default true): witch, heretic and tribrid. Cost x0.75 (rounded up) when the chalk's caster, or the player on the circle's centre (the chalk's 1x2x1 column), is such a species and within the normal altar range of one of the chalk's linked altars; range x1.5 when one stands within the normal range of the altar **as it loads**. Cost is hooked at both places Enchanted charges the altar: the start cost in `GoldChalkBlockEntity.serverTick` and the per-tick `tryConsumePower`. Range is hooked at the three reads of `altarRange` and decided once per altar (`@Unique` cache, until it reloads) so the block count cannot drift. All mixins have `require = 0`: if one misses, the bonus is missing, nothing crashes.
- **Siphoning** (`Siphoning`): sneak + empty main hand + right click on a block with altar power (Enchanted's own entry or one through a block tag) or on a living entity, as a siphoner, heretic or tribrid: +50 `siphonedPower`, cap 1000. A block gives power once per 30 s per player (`SiphonCooldown`, in memory, per position and dimension, cleaned on use and on logout); a creature takes 2 magic damage and gives power only if the hit landed (so its invulnerability frames limit the rate). The click is cancelled when it counts. The damage is `indirectMagic(siphoner, siphoner)`, so PvP rules and claims apply to it and a refused hit gives no power and starts no cooldown. A creature gives power once per 30 s per siphoner (per entity UUID, same in-memory map type, cleaned on logout). The click is cancelled on the client too (sneaking, empty hand, the client's own synced species, and for blocks only if the altar data is known to the client); Forge-style, the server still gets the packet and does the siphoning. This client half is not covered by a GameTest. Each gain is one `BloodlineAccess.set` (one sync); nothing syncs per tick.
- **Paying with siphoned power** (`RiteCost`): for the **start cost only**, the witch discount first, then `siphonedPower` pays as much as it can, the altar the rest. Per-tick costs get the discount but never use siphoned power (it would sync every tick). The siphoned part is taken after `Rite.start()` returned and is dropped by `Rite.cancel()` (`RiteCancelMixin`), so a poor altar or a rite that refuses its target (Ancestral Calling on a heretic, a faction rite with the wrong faction) costs nothing. When siphoned power covers the whole cost the altar is not asked at all, so a **siphoner with enough siphoned power can start a rite with no altar** (the chalk needs no linked altar in that case). Witches do not get that: "cast without an altar" is the siphoner's.
- **Joined the vampires** (`VampireJoin`): `FactionLevelChanged` into the vampire faction from another one applies JOINED_VAMPIRE (witch to nothing, siphoner to heretic).
- **R65:** `PlayerRespawnEvent` (not when leaving the End) applies DIED, which only sets `siphonedPower` to 0; species stays.
- **Not done here:** a witch casting without an altar, the Tensura skills.
- **GameTests**: `WitchGameTests`; the altar tests each run in their own batch at height 200, because a witch near any altar changes it.

## Heretic and tribrid, and the checks (Task 7)

- **Nothing new in the rules.** The wiring was already there: `BloodlineRules` makes a witch who drinks Doppelgänger Blood a TRIBRID (`witchLayer` stays) and refuses a siphoner at `DIED_WITH_ORIGINAL_BLOOD` (`siphoner_hybrid`, the transition never starts); `HybridTraits` covers HYBRID, ORIGINAL_HYBRID and TRIBRID; `WitchAltarBonus.hasBonus` covers WITCH, HERETIC and TRIBRID; `Siphoning.canSiphon` covers SIPHONER, HERETIC and TRIBRID. Task 7 pins it: `hereticKeepsSiphoning`, `witchWerewolfCompletingTransitionBecomesTribrid`, `tribridHasHybridTraitsAndWitchBonus` (real altar cost, traits, block and creature siphoning), `siphonerWerewolfCannotStartTransition`, and `doppelgangerRiteOnlyExistsWithWerewolves` now checks every hybrid rite (`doppelganger_blood`, `hybrid_blood`, `rite_of_the_moon`) is absent without Werewolves and the others (`immortality`, `original_blood`, `ancestral_calling`) are present.
- **Checked by runs, not by hand:** `runGameTestServer`, `-PnoWerewolves` (Originals, witches, heretics; no hybrid rites), `-PnoLinkedMods`, `-PpartsOff=species`, and `runClient` with and without `-PnoLinkedMods` (the log reaches "Loaded 0 entity animations" with no ERROR/Exception/NoClassDefFoundError from this mod).
- **Manual check pending:** the two-client playthrough: Original, make Original's Blood, turn a werewolf friend into a hybrid, Original hybrid, witch, tribrid. Also pending from earlier tasks: the forced-shift heuristic on a real full moon, the downed screen, moonstone has no loot source, rite entity consumption.
- **GameTest cells are 16x1x16 (`structure/empty.nbt`).** The runner force-loads and waits for only the chunks under a cell's box. With the old 1x1x1 template a cell next to a chunk edge had its `+1`...`+13` blocks (and a rite's 8-block radius) in a chunk whose entities do not tick and whose entity section is not visible yet: item drops were not found, FakePlayers and mobs took no damage, a cow stopped ticking. That was the flake in the rite tests (about 1 run in 10, also on the baseline). The cell spacing grows with the box (21 x 22 blocks), which also keeps a rite from reaching a neighbour's cell. **Rule: keep all test positions within 0..15 on x and z** (relative to the cell, no negative offsets); `RiteTestSupport.centre` is (8,1,8) for that reason, and the altar tests put their base at z 4 so a chalk two blocks north stays inside. A test that needs more room widens the template. Failure messages print the target's state through `gametest/Diag`.

## Hunters: roster and rite (plan 7, Task 1)

Package `parts/species/hunter`; GameTests `HunterGameTests`, unit test `FiveRosterTest`.

- **`FiveRoster`** (`SavedData` `supernaturalbloodlines_five`, always the overworld's storage): `members` (the Five, offline ones too), `pendingPotentialChoice` and `liftedCurses` (both for Tasks 2 and 3; read-only views plus `setPendingPotentialChoice` / `setLiftedCurse`). `size()`, `add(UUID)`, `remove(UUID)`, `contains(UUID)`.
- **`HunterEvents`** (registered by `SpeciesPart.init` always, no Werewolves needed): a `BloodlineAccess` listener adds the player when the species becomes HUNTER_OF_THE_FIVE and removes them when it is anything else, so debug and set paths are covered, not only the rite; login re-syncs (`sync`, idempotent); logout does nothing, so the slot stays. `FactionLevelChanged` out of the hunter faction applies `LEFT_BASE_FACTION` with the hunter faction as context (nothing applied that event before; the rules row `HUNTER_OF_THE_FIVE -> NONE` already existed), which frees the slot through the listener.
- **`max_five`** (`SpeciesConfig`, default 5, 1 to 10000, `overrideMaxFive` for tests). `SpeciesContext.of` fills `fiveCount` and `maxFive`; the rules refuse a full Five with `five_full`. Lowering it later does not remove anyone: the Five can sit above it until marks are lost (the config comment says so).
- **Rite** `rite_of_the_five.json`: `faction_rite`, event `rite_of_the_five`, faction `hunter`, medium circle of ritual chalk, power 10000, items 5 `minecraft:candle`, 1 `minecraft:iron_ingot`, 1 `minecraft:book`, 1 `enchanted:taglock` (a plain ingredient), condition `part_enabled species`. Enchanted rite items are plain ids (no tags), and Vampirism has no silver ingot, so the candle is the plain undyed one and the metal is iron.

## Hunters: mark, potentials and curse (plan 7, Task 2)

Package `parts/species/hunter`; GameTests `HunterMarkGameTests` (and `HunterWerewolfGameTests`, only with Werewolves), unit test `FiveRosterTest`. All registered by `HunterEvents.register()`.

- **`MarkTracker`**: one `LivingDeathEvent` listener at `LOW`, `receiveCanceled=false`, so only a real death counts (Vampirism HIGHEST, Original rules HIGH and the Resurrection Ring NORMAL cancel the deaths they stop; the Ash Dagger's release is LOWEST). Prey victim + player killer → `KILLED_PREY` (only HUNTER_OF_THE_FIVE and POTENTIAL are touched); a potential's first kill → `HunterCurse.liftAll`. Marked hunter victim + prey killer (any entity, mobs too) → `KILLED_BY_PREY`, `HunterCurse.curse(killer)` for a player killer, then `PotentialChooser.owe`. "Prey" is `Supernatural.isPrey`, except that a player whose species is WITCH or SIPHONER never is (R81: species wins over faction; the artifacts predicate looks at the faction only). `Supernatural.isPrey` for plain vampire and werewolf players and mobs (by faction id) is registered by `parts/vampirismenchanted/VampirismSupernatural`, called from `VampirismEnchantedPart`, so it holds with artifacts off (pinned by `factionVampireIsPrey` and run with `-PpartsOff=artifacts`). **Kill credit:** the killer is the damage source's entity, else `victim.getKillCredit()`, else the attacker remembered for a death that Vampirism's dying state cancelled (LOWEST, `receiveCanceled=true`, only while `isDBNO()`; weak reference in memory, dropped at the real death and at logout, 10 minutes at most), because the real death of a dying vampire comes later from a source with no attacker.
- **Perks** (`MarkTracker.sync`, idempotent): modifier `supernaturalbloodlines:hunter_mark`, permanent (saved), attack damage `ADD_MULTIPLIED_TOTAL` +1% per kill, movement speed `ADD_MULTIPLIED_BASE` +0.5% per kill, both capped at 20 kills (+20% / +10%). The plan said "multiply base" for the attack; on a player base-multiply is about +0, so the attack uses multiply-total. `BloodlineAccess` listeners hear about species, lineage, rank and `markKills` changes, so every path (rules, the debug event, `set`) syncs the perks; login, respawn and dimension change call it too, and a species change removes the perks. The id is listed in `StalePartModifiers` under SPECIES.
- **`PotentialChooser.owe` / `choose(server, lostMarkOf[, random])`**: `owe` adds one owed potential to the roster and settles what it can; `choose` makes one potential and leaves the roster alone. Candidates: candidates are the online players (`HunterEvents.online`) that are human-like (`SpeciesEligibility`), in the Vampirism hunter faction, species NONE, and not the hunter who just lost the mark. The pick is `random.nextInt` over them (the overworld's random; tests pass a seeded one) and `CHOSEN_AS_POTENTIAL` is applied; a refusal moves on to the next candidate. With no one eligible the choice stays in `FiveRoster.pendingPotentialChoice` (hunter who lost the mark → a count, so the same hunter losing it twice owes two), and `retryPending` runs on `PlayerLoggedInEvent` and on `FactionLevelChanged` into the hunter faction.
- **`HunterCurse`**: the saved flag is `BloodlineState.hunterCurse` (so a second curse changes nothing). Timers are in memory (`UUID → server tick`), `computeIfAbsent` on a curse, dropped on logout, started again at login; `ServerTickEvent.Post` sends one random `HallucinationPayload` when due and reschedules `600 ± 200` ticks later (`tick(server, now)` takes the tick so tests drive it). `FiveRoster.cursed` lists everyone cursed and not yet freed; `liftAll` frees the cursed who are online and moves the rest to `liftedCurses`, which `onLogin` applies. A cure (`DRANK_THE_CURE`) clears the flag; the timer notices and drops itself.
- **`HallucinationPayload`** (core/network, S2C, registered with `BloodlineSyncPayload`): `Kind` PHANTOM, WHISPER, DARKNESS. `send` skips `FakePlayer`s and connections without the channel and returns false. `client/HallucinationClient` (client only; the handler lambda in `ModNetwork` is the only reference): PHANTOM adds a silent, AI-less, invulnerable zombie to the client level only for 5 s (5 to 8 blocks away, facing the player, entity id from the top of the int range so it can never match a server id); WHISPER plays `ambient.cave` locally; DARKNESS gives the local player a 40 tick Darkness effect instance the server never sees; the client tick listener takes it off again (a client never removes an expired effect itself), and a Darkness the server really gave is left alone. No Vampirism hunter skin: it is a plain zombie.
- **Werewolf venom** (`Venom.pulse`) now sends a random `HallucinationPayload` to a player every 600 ticks; Nausea II stays as the fallback for a mob or a client that cannot receive it.
- **Test hooks**: `HunterEvents.overrideOnline` (mock players are not in the player list) and `HallucinationPayload.overrideSpy` (sees every send attempt).
- **Limits**: only a death with a credited attacker counts; a vampire that dies of the dying state's timer after more than 10 minutes, or whose attacker logged out, is no kill. The client side of the hallucinations was only checked for loading (`runClient` log), not for how it looks.

## Hook points (verified)

Checked with `javap` on the jars in the Gradle cache: Vampirism 1.21-1.10.13, Werewolves 1.21-2.0.3.4, Enchanted 4.2.7. Earlier notes (rite lifecycle, altar data, `BloodDrinkEvent`, `PlayerFactionEvent`) are in [enchanted_tensura](enchanted_tensura.md), [vampirism_tensura](vampirism_tensura.md) and [vampirism_enchanted](vampirism_enchanted.md) and are not repeated.

### Werewolves (optional; touch only behind `ModList.isLoaded("werewolves")`)

- **Player access:** `WerewolfPlayer.get(Player)` / `getOpt(Player)` / `getOptSave(Player)` / `getOptEx(Entity)` (package `de.teamlapen.werewolves.entities.player.werewolf`). API interface `IWerewolfPlayer` (`...api.entities.player`), faction `WReference.WEREWOLF_FACTION`. `Helper.isWerewolf(Player)`, `Helper.canBecomeWerewolf(Player)`.
- **Form API:** `WerewolfPlayer.getForm()`, `switchForm(WerewolfForm)`, `setForm(WerewolfFormAction, WerewolfForm)`. `WerewolfForm` constants `NONE`, `HUMAN`, `BEAST`, `BEAST4L`, `SURVIVALIST`; `isTransformed()`, `isHumanLike()`. `FormHelper.getForm(LivingEntity)`, `FormHelper.isFormActionActive(IWerewolfPlayer)`, `FormHelper.getActiveFormAction`, `FormHelper.deactivateWerewolfActions`. A shift is a Vampirism action: the three `WerewolfFormAction`s are toggled through `ActionHandler.toggleAction(action, new ActivationContext())`.
- **Full-moon helper:** `de.teamlapen.werewolves.util.Helper.isFullMoon(Level)` is `!hasFixedTime && 12786 < dayTime % 192000 < 23216` (the night of moon phase 0; not our `MoonRule`, which is the whole phase-0 day). `Helper.isNight(Level)`.
- **Forced full-moon shift:** `WerewolfPlayer.onUpdate()`, once per second (`gameTime % 20 == 0`): if `Helper.isFullMoon`, no form action active and the player does not have the skill `ModSkills.FREE_WILL`, it toggles `lastFormAction` (else any form action the player can use) through `ActionHandler.toggleAction`. **There is a cancellable hook, no mixin needed:** `ActionHandler.toggleAction` fires `ActionEvent.ActionActivatedEvent` (a NeoForge `ICancellableEvent`, API package `de.teamlapen.vampirism.api.event`) before activating, and a cancel returns `IAction.PERM.DISALLOWED`. The forced call runs inside Vampirism's `EntityEventHandler.onPlayerUpdate(PlayerTickEvent.Post)`; a voluntary shift comes from a network packet, outside any player tick. So a listener can tell them apart with a thread-local "inside a player tick" flag (set in `PlayerTickEvent.Pre`, cleared in the last `PlayerTickEvent.Post` listener) and cancel only then. Simpler alternative: grant `FREE_WILL`, but it is a skill the player can lose or see in the tree. This is Task 4's call (hybrids shift at will); plan 9's `MoonControl` can reuse the same listener.

### Vampirism

- **Blood drink events:** `BloodDrinkEvent` (not cancellable) with `PlayerDrinkBloodEvent` (fired by `VampirePlayer.drinkBlood(int, float, boolean, IDrinkBloodContext)` through `VampirismEventFactory.fireVampirePlayerDrinkBloodEvent`) and `EntityDrinkBloodEvent`. Both only exist for vampires (`IVampire`). **Bottles:** `BloodBottleItem.finishUsingItem` only drinks when the user is an `IVampire` (`IVampire.drinkBlood(int, float, DrinkBloodContext(ItemStack))`); for anyone else it falls back to `Item.finishUsingItem`. `PureBloodItem`, `VampirismItemBloodFoodItem` and `FeedingAdapterItem` also call `drinkBlood`. **Consequence for Task 3:** a werewolf (the transition happens in the werewolf faction) fires no Vampirism blood event, so "drank doppelgänger blood / other blood" must come from our own items (`LivingEntityUseItemEvent.Finish` on `DoppelgangerBloodItem` and Original's Blood) and from whatever the spec lets a werewolf drink; do not wait for `BloodDrinkEvent`.
- **Bite:** `VampirePlayer.biteEntity(int)` / `onBite(IVampire)`, `determineBiteType(LivingEntity)` (see vampirism_tensura for the mixin that uses it).
- **Dying / DBNO (R32): the API exists.** `IVampirePlayer.isDBNO()`, `IVampirePlayer.onDeadlyHit(DamageSource): boolean` (returns true when it put the player into the state; `VampirePlayer` also has `getDbnoTimer()`, `getDbnoDuration()`, `giveUpDBNO()`). Vampirism calls it from `ModPlayerEventHandler.onLivingDeathFirst(LivingDeathEvent)` and cancels the death when it returns true. It only works for a player with Vampirism level > 0 (`VampirePlayer.getLevel() > 0`), without the `NEONATAL` effect, when `Helper.canKillVampires(source)` is false (that is true for `bypasses_invulnerability`, the `vampirism:vampire_immortal` tag and the config list `vpImmortalFromDamageSources` for living direct attackers that are not hunters, among others). The state: health is reset, forced pose SLEEPING, a timer (exact values not checked); "give up" calls `giveUpDBNO()`. So an **Original (vampire faction) already gets Vampirism's dying state** for ordinary lethal damage, and Task 2 only has to make white oak kill (`canKillVampires`/our listener at higher priority) and keep void and `/kill` lethal. An **Original hybrid is in the werewolf faction (level 0 as a vampire), so `onDeadlyHit` returns false for it**: Task 2 needs its own downed state for that species, as the ledger says.
- **Items:** `vampirism:human_heart`, `vampirism:weak_human_heart` (already in vampirism_enchanted.md).

### Enchanted 4.2.7

- **Rite JSON `entities` and `time`:** `RiteType.entities` is a `List<EntityType<?>>` of **ingredients**, not a condition on the caster or target: `GoldChalkBlockEntity.tryConsumeEntity` looks for entities of those types in the circle bounds and calls `Entity.kill()` on them (so `minecraft:player` there would kill a player). `time` is `[from, to]`, compared with `Level.getDayTime()` in `RiteType.matches` (no moon phase, and it is a day time, not a time of day modulo). `dimensions` and `weather` are the other `matches` conditions. Consequence: "the target has to be an Original" can only be a check in our own factory's `onStart` (as plan 4 Task 2 says), never in the JSON.
- **Altar range (witch x1.5):** `ServerConfig.INSTANCE.altarRange` (`ModConfigSpec.IntValue`), read at three sites in `AltarBlockEntity`: `firstTick()`, the private `setupBlockData()` (the scan of the altar's blocks) and the public `posWithinRange(BlockPos)` (does a gold chalk lie inside the altar's box; the box is `range` wide and `range + 1` along the altar's facing axis). The altar has **no owner or caster**: a witch bonus on the range has to look at a player (for example the one standing in the circle) from the chalk side, or widen `posWithinRange` for a position known to be a witch's chalk.
- **Rite power cost:** the start cost is paid in `GoldChalkBlockEntity.serverTick(Level, BlockPos, BlockState, GoldChalkBlockEntity)` after every item and entity is consumed: `PowerHelper.tryGetProvider(level, chalk.getPosHolder())` then `PowerProvider.tryConsume((double) RiteType.getPower())`. The per-tick cost is `GoldChalkBlockEntity.tryConsumePower(int)` (called by `Rite.tick()` with `tickPower`), which does the same `tryConsume` on the provider. The caster is the chalk's private `UUID caster`, set in `GoldChalkBlockEntity.use(Level, BlockPos, Player)`; `Rite.RiteParams.caster` is the same id. So the witch x0.75 mixin has two `tryConsume` call sites in `GoldChalkBlockEntity` (the `(double)` argument can be scaled with a `@ModifyArg`), plus `tryConsumePower(int)`; the siphoner paying from `siphonedPower` replaces the provider call at the same two places.
- **The altar a rite uses, and its power:** `Rite.getLevel()` / `getPos()` give the level and the chalk position; `level.getBlockEntity(pos)` is the `GoldChalkBlockEntity` (a `PowerConsumer`); `PowerHelper.tryGetProvider(level, chalk.getPosHolder())` returns the `PowerProvider` (an `AltarBlockEntity`; `PowerPosHolder.getPositions()` lists the linked altar positions). `AltarBlockEntity` has **no public getter for the stored power** (field `power` is private; capacity is on `AltarMenu`); the only public power method is `tryConsume(double)`. Read it only through a mixin accessor or reflection, or avoid needing it.
