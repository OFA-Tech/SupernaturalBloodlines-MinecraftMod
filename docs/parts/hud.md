**Mixin budget: 0 of 3 used.** Reserved, each added only after its task shows that no event or API works (see `docs/mixins.md`): (1) `AbilityStorageNextPresetMixin` (13b Task 2), (2) `VampireRaceFeedMixin` (13c Task 2), (3) `KeyBindsListHideMixin` (13a Task 4). `HudMixinPlugin` follows `PartMixinPlugin` and applies each future mixin only when its target mods are installed (a map from the mixin's simple class name to mod ids).

**Done so far (phase 13a, Tasks 1 to 3):** the part and its configs, the Bite rules and the server bite, the turning bite. Not yet: the keymap, the slots and the HUD (13a Task 4 and 13b).

- `shared/supernatural/HybridFeed`, `shared/supernatural/TurningFeed`, `shared/vampirism/BloodlessPlayers`: hooks the other parts install, so the HUD never imports them (parts never import each other). Each defaults to "nobody is a hybrid / in the turning / bloodless".
  - `HybridFeed` and `TurningFeed`: installed by `SpeciesPart`. `HybridFeed.isHybrid` = `HybridTraits.isHybrid(species)` with Werewolves loaded; `feed` = `BloodThirst.addThirst(p, GAIN)`. `TurningFeed.canFeed` = `inTurning && TurningHandler.wouldComplete(p)`; `feed` = `TurningHandler.drankHumanBlood`.

- `parts/hud/client/`: `HudClient` (empty so far; registered only behind `Dist.CLIENT` from `HudPart`) and `HudClientConfig`.

## The slot model, the loadout and the payloads (13b Task 1)

- `core/hud/` (pure): `PresetPair` (`left = active`, `right = (active + 1) % presetCount`; Tensura has 9 presets, so 9 pairs with 1), `SlotMode` (`TENSURA` / `SUPERNATURAL`: which exist for the installed mods, the next one on a toggle, the start mode from the client `mode` setting), `SlotView` (what a slot shows: icon, key label, cooldown fraction and seconds, active, greyed reason, name, detail), `Loadout` (the six Supernatural-mode slots), `RateLimiter`.
- **`Loadout`**: six `Optional<ResourceLocation>`. `Loadout.DEFAULT` has `supernaturalbloodlines:bite` in slot 1 and nothing else, and is the attachment default. It is saved as a list of six strings (`""` for an empty slot), so a cleared Bite stays cleared: **it is never put back on its own**. A missing tag is the default, a short or long list is padded or cut, a bad id is an empty slot. Attachment `hud_loadout` (`ModAttachments.HUD_LOADOUT`, `copyOnDeath`).
- **What a player may assign** (`LoadoutService.set`, the only writer): Bite always; any other id only if Vampirism is installed, the id is in its action registry, and the player's **current faction** has it unlocked (`FactionActions.unlocked`: `matchesFaction` and `isActionUnlocked`; the Werewolves player is an `IFactionPlayer` too, so a hybrid gets Werewolves actions). Duplicates are allowed. A faction change never clears the list. Refusals: `hud.loadout.bad_slot`, `unknown_action`, `not_unlocked`.
- **Payloads** (`HudNet`, optional registrar, version 1): `SetLoadoutPayload(slot, actionId)` C2S (an empty id clears), `LoadoutSyncPayload(loadout)` S2C (login, respawn, dimension change and every change). **Every payload that asks for something counts against `rate_limit_per_second`, refusals included** (`HudNet.allowed`, a `RateLimiter` window of 20 ticks per player); one over the limit is dropped without an answer, so a flood cannot make the server talk back. Released keys are not limited (a dropped release would leave a feeding running, and a release does nothing unless something is held).
- `shared/hud/LoadoutAccess`: what the hub's Loadout tab (13b Task 5) sees: `available()`, `get()`, `assignable()` (Bite first), `set(slot, id)`, `keyLabel(slot)`. The HUD client installs `ClientLoadout`; without the HUD part it is unavailable. `ClientActions` (the only client class that links Vampirism) lists the unlocked actions; an action's icon is `<namespace>:textures/actions/<path>.png`.
- Tests: `PresetPairTest`, `SlotModeTest`, `LoadoutTest`, `RateLimiterTest`; GameTests `LoadoutGameTests` (`newPlayerHasBiteInSlotOne`, `biteCanMoveAndClear`, `aClearedLoadoutIsNotPutBackAfterTheSaveRoundTrip`, `badSlotsAndBadIdsAreRefused`, `loadoutSurvivesDeath`, `payloadIdAndSlotAreOnlyNames`, `everyLoadoutPayloadCountsAgainstTheRateLimit`) and `LoadoutVampirismGameTests` (`setLoadoutAcceptsUnlocked`, `setLoadoutRefusesLockedOrForeign`, `anActionOfAnotherFactionIsNotAssignableEvenIfUnlockedElsewhere`, `loadoutNotClearedOnFactionChange`).

## The keymap and covered keys (13a Task 4)

- `core/hud/HudKeyDefaults` (pure data) holds our defaults; `parts/hud/client/HudKeys` builds the mappings from it: `key.supernaturalbloodlines.slot_1..6` (R F V Z X C) and `hud_mode` (**Alt + Caps Lock**, `KeyModifier.ALT`), all in `PackKeybinds.CATEGORY`, context `IN_GAME`. The hub key (Home) stays in the supernatural part. **No Bite key.** The keys do nothing until 13b.
- `core/hud/CoveredKeys` (pure): the record/unbind/restore rules (see its javadoc). `KeyCover` applies them: covered ids are `tensura.keybinding.ability.slot_1..3`, `tensuraslots.keybinding.secondary_ability.slot_1..3`, `keys.vampirism.suck`, `keys.vampirism.action1..9`, `keys.werewolves.bite` (names read from each mod's lang file). It finds keys by name, so an uninstalled mod's keys are simply absent. It runs on the first client tick (NeoForge 1.21.1 has no `ClientStartedEvent`; the options are loaded and every mod has registered its keys by then), when `hide_covered_keys` changes (compared on the tick, no per-frame scan) and when the Controls screen closes (Reset All puts covered keys back on their defaults). The record is `config/supernaturalbloodlines-hud-keys.json` (an unreadable one is moved to `.bad`, never overwritten). With the part off, the main class registers `KeyCover.registerRestoreOnly()` on the client so the recorded binds still come back.
- **Never losing a bind (final review).** `KeyCover` builds a `CoverRun` (core, pure, tested with fakes) over the game's keys and a `RecordFile`. Covering writes the record **first** and touches no key if that fails (`record_not_saved`); restoring sets and saves the keys **first** and drops the record entries **after** (a crash leaves a stale record, never an unbound key with no record). `RecordFile` writes `.tmp` then `ATOMIC_MOVE`; an unreadable file is renamed `<file>.bad-<millis>[-n]` (never replaced), and while any `.bad*` file exists (or one could not be set aside) nothing is written and nothing is covered (`covering()` is false, so Controls shows the keys too). A recorded bind that cannot be parsed stays in the record. A recorded id that is no longer in `COVERED` is restored even while covering. Manual recovery is in `wiki/Key-Binds.md`.
- `KeyHiding`: **no mixin.** On `ScreenEvent.Init.Post` it removes the covered entries from `KeyBindsScreen.keyBindsList` (access transformer: `keyBindsList` and `KeyBindsList$KeyEntry.key`). Controlling 19.0.5 (read with javap): `NewKeyBindsScreen extends KeyBindsScreen`, its `NewKeyBindsList extends CustomList extends KeyBindsList`, its entries are its own `KeyEntry` (public `getKey()` from `IKeyEntry`), and `filterKeys` rebuilds `children()` from `CustomList.allEntries` (public field, `getAllEntries()`). So the same removal is done on `allEntries`, which keeps the search from bringing them back. The reserved `KeyBindsListHideMixin` stays unused. **Checked in a real dev client (2026-11-15, `runClient` with Controlling 19.0.5, Searchables and Tensura Slots in `run/mods`):** the covered keys are gone from the list and from Controlling's search (`Activation` finds nothing; `Ability` still finds Next/Previous Ability Mode and Race/Mount Ability; `category:Vampirism` lists only Minion task, Select Arrow Type, Skill Screen, Switch vision, Use Actions and Vampirism Menu), so the reserved mixin is **not** needed. Setting `hide_covered_keys = false` while the game runs logged `Covered keys: restored [...]`, put the binds back in `options.txt` (Alt modifiers kept: `key.keyboard.1:ALT`) and emptied the record; after a restart with it `false`, the search shows Ability 1 to 6 Activation with their binds (Z X C and numpad 1 2 3). Screenshots: `.superpowers/sdd/13a-keys/t13a-*.png` (not committed, the folder is ignored).
- **Alt + Caps vs the Caps radio key.** `KeyMappingLookup.getAll(key, fallback)` collects the mappings of the active modifiers for that key; the unmodified ones are added only as a fallback for a key that is itself a modifier. So Alt + Caps should fire `hud_mode` only. **Checked in a real dev client** with a temporary stand-in for the radio (a plain Caps Lock mapping in the same category, not committed): in a world, Alt + Caps fired only `hud_mode`, and Caps alone fired only the plain mapping.
- Tests: `CoveredKeysTest` (`recordsBeforeUnbinding`, `restoresPlayersOwnBind`, `restoreSkipsKeysThePlayerRebound`, `secondRunRecordsNothingNew`, `missingModIgnored`, and more), `HudKeysDefaultsTest`.

## The Bite action (R110, R20e)

Bite is an action, not a key. Nothing fires it yet: 13b Task 1 puts it in the loadout (slot 1 by default) and 13b Task 3 fires it from its slot. Until then the GameTests call `BiteService` directly. The rules are in `SPECIES-RULES.md` R110; the table is `BiteRules.decide(BiteContext)`, first match wins. `BiteService.context` builds the context: the faction id comes from Vampirism's `getCurrentFaction()`, `wolfForm` is Werewolves' `getForm().isTransformed()`, `hybridType` is `HybridFeed.isHybrid`, `inTurning` is the saved state and `turningWouldComplete` is `TurningFeed.canFeed`. Without Vampirism every press is `NONE` (`needs_vampirism`).

A press resolves the target first: in the same level (`level.getEntity(id)`, so a target in another level is "no target"), alive, not the player, within `bite_reach` (`distanceTo`), in line of sight. Then, by action:

| Action | How |
|---|---|
| `WEREWOLF_BITE` | Werewolves' own `canBite()`, `canBiteEntity(LivingEntity)` and `bite(int)` through method handles on the runtime class of the API's `IWerewolfPlayer` (`WerewolfPlayer` extends a Vampirism class that is only in the full jar). Venom (R42v) and everything else is Werewolves' |
| `VAMPIRISM_DRINK` | `determineBiteType(target)` must not be `NONE` and the vampire's level must be above 0, then `VampirePlayer.biteEntity(int)` on press and `endFeeding(true)` on release. Both are public but only in the full jar: `VampirismBite` looks them up once with `MethodHandles.publicLookup()` on the runtime class; a miss logs one warning and the bite does nothing. Vampirism's feeding runs in its own per-tick player update. Venom R42 and the bloodless refusal (`VampirePlayerBiteMixin`) still apply |
| `HYBRID_FEED` | Refused at thirst 20 (`thirst_full`) and when the victim has no blood (`no_blood`). Then `target.hurt(playerAttack(p), 2)` (the player is the direct entity, so `Venom.onDamaged` poisons a vampire victim by itself) and `HybridFeed.feed` (+5) |
| `TURNING_BITE` | `HumanLikeBlood.test(target)` or `not_human`. Then 1 damage of `supernaturalbloodlines:turning_bite` (caused by the player; the type is in the `is_player_attack` and `panic_causes` tags), the bite sound, and `TurningFeed.feed` |

A victim has blood by Vampirism's own values (`VampirismBite.blood`): a `PathfinderMob`'s `IExtendedCreatureVampirism.getBlood()` (the `entity_blood` data map); a **vampire** player's `getBloodStats().getBloodLevel()`; a **player who is not a vampire** (vampire level 0) has their **food level** (read from `VampirePlayer.onBite`, which takes `getFoodData()` below level 1; its blood stats are unused there); 0 for `BloodlessPlayers.test`. `drain` takes from the same place (`useBlood`, or `setFoodLevel`). `GameTest hybridFeedOnAHumanPlayerTakesFood`. A vampire mob and a converted creature have none. The hybrid feed **takes 2 of it** (`HYBRID_BITE_BLOOD`; a mob's `setBlood`, a player's `useBlood`) and a drained victim gives nothing (`no_blood`), so one creature cannot be farmed; the blood comes back the way Vampirism's own does. The hybrid feed and the turning bite first ask `CommonHooks.onPlayerAttackTarget(p, target)` (the attack event, which claim and PvP mods cancel; a cancelled bite is `cannot_bite_target`, with nothing drained, hurt or fed).

The biter must be alive, awake and not a spectator (`cannot_bite`, checked first). `VAMPIRISM_DRINK` reach is also clamped to the player's `ENTITY_INTERACTION_RANGE` (3), because Vampirism's `biteEntity` silently does nothing beyond it, which would otherwise look like a bite that worked and start the cooldown. Vampirism has no public feeding state to read afterwards (`getFeedProgress` is a tick counter that starts at 0), so the other silent refusals of `biteEntity` are checked before it: a dying player (`isDBNO`) and an active bat form (`isActionActive(vampirism:bat)`, untested: bat form needs unlocked skills) are `cannot_bite`. `bite_reach` is 1 to 16. One bite per 20 ticks per player (`cooldown`), set only by a bite that happened. Every refusal is an action bar line `supernaturalbloodlines.hud.bite.<reason>`. **13b:** `rate_limit_per_second` applies to every press payload, refusals included.

`BiteService.context` is private: it links Vampirism, so only `actionFor` (which checks `ModList.isLoaded("vampirism")`) reaches it. `HybridFeed.isHybrid` needs the species `isHybrid`, Werewolves loaded **and** the werewolf faction.

### Verified for 13a Tasks 2 and 3 (javap and GameTests, 2026-11-15)

- **Werewolves classes.** `de.teamlapen.werewolves.entities.player.werewolf.WerewolfPlayer` (note `entities`, not `entity`), `de.teamlapen.werewolves.api.entities.werewolf.WerewolfForm`, `de.teamlapen.werewolves.api.entities.player.IWerewolfPlayer` (its `getForm()` comes from `IWerewolf`). `WerewolfPlayer` extends `de.teamlapen.vampirism.entity.player.FactionBasePlayer`, which is not on the compile classpath (API jar only), so `WerewolfPlayer.get(p)` does not compile. Everything on it is reached through the API interface or a method handle.
- **The "wolf form" getter.** `WerewolfForm` has `isHumanLike()` and `isTransformed()`. Constructor flags: `NONE` (humanLike, not transformed), `HUMAN` (the half form: humanLike **and transformed**), `BEAST`, `BEAST4L`, `SURVIVALIST` (not humanLike, transformed). `WerewolfPlayer.canBite()` begins with `getForm().isTransformed()`, so `NONE` can never bite. **R110's "wolf form" is therefore `isTransformed()`**, not "anything but `HUMAN`": a werewolf in the half form (`HUMAN`) takes row 1, and an untransformed one (`NONE`) is row 4, which Werewolves itself refuses (`cannot_bite`). `canBite()` also needs the `BITE` permission node; `canBiteEntity` needs reach and, for a player victim, `BITE_PLAYER`.
- **Vampirism's "this creature has blood" getter.** `VampirismAPI.getExtendedCreatureVampirism(PathfinderMob) -> Optional<IExtendedCreatureVampirism>`, with `getBlood()` / `setBlood(int)` / `getMaxBlood()`. A villager has blood. A plain `IronGolem`, a `vampirism:vampire` and a `vampirism:villager_converted` have none (`setBlood` is capped by the max, which is 0). A player's blood is `IVampirePlayer.getBloodStats().getBloodLevel()` (the food level below vampire level 1), taken with `useBlood(n, true)`. Vampirism's own feeding reads the same values (`VampirePlayer.biteFeed`: `ExtendedCreature.getSafe` for creatures, `onBite` for players).
- **A FakePlayer is not ticked.** Vampirism's feeding (`updateFeeding`) runs in `VampirePlayer.onUpdate()` from the player tick, so GameTests that need the feeding to progress call `onUpdate()` themselves (`Feeding.tick`). `level.getEntity(id)` does not find a FakePlayer, so GameTests use mobs as victims.
