# Part: hud

Requires: **no mod**. Tensura, Vampirism and Werewolves are optional extras inside the part, the way Werewolves is inside species: each is reached only through an adapter class that is touched after `ModList.isLoaded(...)`. Package: `net.ofatech.supernaturalbloodlines.parts.hud`. Config key `hud`, files `supernaturalbloodlines-hud.toml` (common) and `supernaturalbloodlines-hud-client.toml`. Plan: `docs/superpowers/plans/2026-11-15-supernatural-hud.md` (plan 13). Spec: `docs/superpowers/specs/2026-11-14-supernatural-hud-design.md`.

**Mixin budget: 1 of 3 used** (see `docs/mixins.md`): (1) `AbilityStorageNextPresetMixin` (13b Task 2) **used**, because Tensura's server refuses a skill in preset N+1 otherwise. Still reserved, each added only after its task shows that no event or API works: (2) `VampireRaceFeedMixin` (13c Task 2), (3) `KeyBindsListHideMixin` (not needed: 13a Task 4 hides the keys without it). `HudMixinPlugin` follows `PartMixinPlugin` and applies each future mixin only when its target mods are installed (a map from the mixin's simple class name to mod ids).

**Done so far (phase 13a, Tasks 1 to 3):** the part and its configs, the Bite rules and the server bite, the turning bite. Not yet: the keymap, the slots and the HUD (13a Task 4 and 13b).

## Layout

- `core/hud/` (pure, no game classes): `BiteRules`, `BiteAction`, `BiteContext`.
- `shared/supernatural/HybridFeed`, `shared/supernatural/TurningFeed`, `shared/vampirism/BloodlessPlayers`: hooks the other parts install, so the HUD never imports them (parts never import each other). Each defaults to "nobody is a hybrid / in the turning / bloodless".
  - `HybridFeed` and `TurningFeed`: installed by `SpeciesPart`. `HybridFeed.isHybrid` = `HybridTraits.isHybrid(species)` with Werewolves loaded; `feed` = `BloodThirst.addThirst(p, GAIN)`. `TurningFeed.canFeed` = `inTurning && TurningHandler.wouldComplete(p)`; `feed` = `TurningHandler.drankHumanBlood`.
  - `BloodlessPlayers`: installed by `VampirismTensuraPart` (`FactionRaceRules.isBloodless`).
- `parts/hud/bite/`: `BiteService` (server; `press(player, targetId)`, `release(player)`, `actionFor(player)`, `cooldownLeft(player)`), `VampirismBite` and `WerewolfBite` (adapters; the only classes that touch the mods).
- `parts/hud/client/`: `HudClient` (empty so far; registered only behind `Dist.CLIENT` from `HudPart`) and `HudClientConfig`.

## The slot model, the loadout and the payloads (13b Task 1)

- `core/hud/` (pure): `PresetPair` (`left = active`, `right = (active + 1) % presetCount`; Tensura has 9 presets, so 9 pairs with 1), `SlotMode` (`TENSURA` / `SUPERNATURAL`: which exist for the installed mods, the next one on a toggle, the start mode from the client `mode` setting), `SlotView` (what a slot shows: icon, key label, cooldown fraction and seconds, active, greyed reason, name, detail), `Loadout` (the six Supernatural-mode slots), `RateLimiter`.
- **`Loadout`**: six `Optional<ResourceLocation>`. `Loadout.DEFAULT` has `supernaturalbloodlines:bite` in slot 1 and nothing else, and is the attachment default. It is saved as a list of six strings (`""` for an empty slot), so a cleared Bite stays cleared: **it is never put back on its own**. A missing tag is the default, a short or long list is padded or cut, a bad id is an empty slot. Attachment `hud_loadout` (`ModAttachments.HUD_LOADOUT`, `copyOnDeath`).
- **What a player may assign** (`LoadoutService.set`, the only writer): Bite always; any other id only if Vampirism is installed, the id is in its action registry, and the player's **current faction** has it unlocked (`FactionActions.unlocked`: `matchesFaction` and `isActionUnlocked`; the Werewolves player is an `IFactionPlayer` too, so a hybrid gets Werewolves actions). Duplicates are allowed. A faction change never clears the list. Refusals: `hud.loadout.bad_slot`, `unknown_action`, `not_unlocked`.
- **Payloads** (`HudNet`, optional registrar, version 1): `SetLoadoutPayload(slot, actionId)` C2S (an empty id clears), `LoadoutSyncPayload(loadout)` S2C (login, respawn, dimension change and every change). **Every payload that asks for something counts against `rate_limit_per_second`, refusals included** (`HudNet.allowed`, a `RateLimiter` window of 20 ticks per player); one over the limit is dropped without an answer, so a flood cannot make the server talk back. Released keys are not limited (a dropped release would leave a feeding running, and a release does nothing unless something is held).
- `shared/hud/LoadoutAccess`: what the hub's Loadout tab (13b Task 5) sees: `available()`, `get()`, `assignable()` (Bite first), `set(slot, id)`, `keyLabel(slot)`. The HUD client installs `ClientLoadout`; without the HUD part it is unavailable. `ClientActions` (the only client class that links Vampirism) lists the unlocked actions; an action's icon is `<namespace>:textures/actions/<path>.png`.
- Tests: `PresetPairTest`, `SlotModeTest`, `LoadoutTest`, `RateLimiterTest`; GameTests `LoadoutGameTests` (`newPlayerHasBiteInSlotOne`, `biteCanMoveAndClear`, `aClearedLoadoutIsNotPutBackAfterTheSaveRoundTrip`, `badSlotsAndBadIdsAreRefused`, `loadoutSurvivesDeath`, `payloadIdAndSlotAreOnlyNames`, `everyLoadoutPayloadCountsAgainstTheRateLimit`) and `LoadoutVampirismGameTests` (`setLoadoutAcceptsUnlocked`, `setLoadoutRefusesLockedOrForeign`, `anActionOfAnotherFactionIsNotAssignableEvenIfUnlockedElsewhere`, `loadoutNotClearedOnFactionChange`).

## Tensura mode: slots, input and hiding Tensura's HUD (13b Task 2)

**The open hook, checked first (javap, then GameTests `TensuraPresetGameTests`): Tensura's server DOES refuse a skill that is only in preset N+1.** Tensura's `AbilityHandler` answers ManasCore's `SkillEvents.ACTIVATE_SKILL` with `interruptFalse` unless `IAbility.isAbilityInActivePreset(keyNumber, skill, mode)`, and all four overloads look only at the active preset. `SkillStorage.startHoldSkill(id, keyNumber, mode)` (what the activation packet calls) returned false for a skill in the next preset and true in the active one, and the passive checks (`TensuraSkill.isInSlot`) are false for it too. So reserved mixin (1) is **used**: `AbilityStorageNextPresetMixin` (see `docs/mixins.md`): the tests were red without it and are green with it. Tensura Slots does the same with `IsAbilityInActivePresetMixin`, which is what the pack drops; both can be installed (the second sees `true` and returns).

Facts read from the jars (corrections to the plan marked **fix**):
- **The key number is the slot index inside its preset (0 to 2), for both columns.** Tensura's own keys send `skillActivationPacket(id, slot, mode)`; so do Tensura Slots' secondary keys (`getAbilitySlot(preset N+1, slot)`, `skillActivationPacket(id, slot, mode)`).
- **Fix: release is `skillReleasePacket(id, keyNumber, mode)`, not `(id, keyNumber, heldTicks)`.** `RequestSkillReleasePacket` is `(keyNumber, mode, skillId)`; ManasCore counts the held ticks itself. (Tensura Slots passes `mode` and `held/50` there, which looks like a bug.)
- **Fix: `changeModePacket(int slot, int presetId, boolean alternative)`.** The two-argument form is `(slot, -1, alt)`, and the server's `changeMode` uses `presetId` when it is not -1, so the mode change of a right-column slot is applied on the server. The plan had the first two arguments the other way round.
- `HudConfig.abilities.render` is read by Tensura's HUD each frame; `ConfigRegistry` is `io.github.manasmods.manascore.config.ConfigRegistry`; the config is saved through `SettingsOptions.saveAll()` from `SettingsScreen.onClose()` (and `OverlayHandler.savePositionById`), so that screen is the only time our lowered flag could be written to disk. The cooldown is only `getCoolDown(mode)` (ticks left), no total, so the fill is `left / the longest seen since ready`.
- The slot's skill icon is `ManasSkill.getSkillIcon()`; a mode's name is `TensuraSkill.getModeName(instance, mode)`.

What was built:
- `core/hud/InputPlan` (pure, `InputPlanTest`): the forwarding table (activate, change mode with its preset id, release). `core/hud/HudFlagGuard` (pure, `HudFlagGuardTest`): the in-memory flag we lower and give back.
- `parts/hud/client/`: `HudModeState` (start mode from the `mode` setting, `hud_mode` toggles), `HudSlots` (the six `SlotView`s, rebuilt once per client tick), `HudInput` (the six keys and the mode key). **A slot key is watched by its physical state**, not `KeyMapping.isDown()`: NeoForge only fires a mapping whose modifier matches the held modifiers, so a plain R mapping would be silent while Alt is held, and Alt + slot key is Tensura's mode change. Only with a world open and no screen, and only with `hud_enabled`. With `hide_covered_keys` off while the HUD is on, Tensura's own keys and ours would both fire: turn the HUD off first (`hud_enabled = false`).
- `parts/hud/client/tensura/` (linked to Tensura, reached after `ModList.isLoaded("tensura")`): `TensuraSlots` (active preset for 1 to 3, `PresetPair.right` for 4 to 6; cooldown, toggled, greyed when the skill is missing or `canInteractSkill` is false), `TensuraInput`, `TensuraHudFlags`.
- **`TensuraHudFlags`** lowers `abilities.render` while our HUD is shown and `hide_tensura_skill_hud` is on, gives it back when ours goes off, when the world is left, and while Tensura's `SettingsScreen` is open (so ManasCore saves the player's value); what the player leaves in that screen is theirs. **Until the HUD layer of 13b Task 4 exists the "our HUD is shown" signal is false, so nothing is hidden yet.** With Tensura Slots still installed, its own second column keeps drawing (hiding it is a Task 4 job; its keys are covered).
- Supernatural mode sends nothing yet (13b Task 3).
- `AbilityStorageNextPresetMixin` (`mixin/hud`, `@Pseudo` string target, `require = 0`, applied only with Tensura, switch `next_preset_active`; `HudMixinPlugin.postApply` logs whether all four hooks landed) and `parts/hud/tensura/NextPreset` (the rule: the skill is in preset N+1 at that slot and mode; a malformed list never breaks Tensura's own answer).

Tests: `InputPlanTest` (left press, right press with the same key number, Alt + left, Alt + right with the next preset's id, preset 9 pairs with 1, Next wins over Previous, empty slot, release carries the pressed skill and mode), `HudFlagGuardTest`, and `TensuraPresetGameTests` (`aSkillInTheActivePresetCountsAsActive`, `aSkillInTheNextPresetCountsAsActiveForTheFourChecks`, `theActivationPacketAcceptsASkillInTheNextPreset`, `thePresetAfterTheLastIsTheFirst`, `onlyTheNextPresetCountsAndOnlyAtItsSlot`). **Not checked in a running client** (the owner is playing): the manual parity checks of the plan (a press skill, a held skill, a toggle skill, a mode-cycling skill, Alt + scroll through the 9 presets, opening and closing Tensura's HUD settings).

## Supernatural mode: the action slots and the triggers (13b Task 3)

- **`TriggerActionPayload(slot, targetEntityId, release)`** C2S, handled by `HudNet.handleTrigger`. **The action is read from the player's own loadout, never from the packet**, which carries only a slot number and what the crosshair was on. A press counts against `rate_limit_per_second`, refusals included (an empty slot, a locked action, a cooldown); one over the limit is dropped without an answer. A release is not limited (see Task 1).
- **`ActionService.trigger`** (links no Vampirism type, so it loads on a server without Vampirism): an empty slot is `empty_slot`; **Bite** goes to `BiteService.press(player, target)` on press and `release(player)` on release (the vampire's feeding ends); any other id needs Vampirism, a living awake non-spectator player, and the action unlocked in the player's current faction (`not_unlocked`), then `FactionActions.toggleFor` calls Vampirism's `toggleAction(action, context)` exactly like its own key. The context is built on the server: the block the player looks at (`pick`, at most 5 blocks), and the creature the client's crosshair named, kept only if it is alive, in the same level, within `bite_reach` and in sight. A refused `PERM` is `hud.action.<perm>` (`disabled`, `disallowed`, `cooldown`, `permission_disallowed`, `not_unlocked`); each is an action bar line. A lasting action toggles off with the second press, which Vampirism does not ask a cooldown for.
- **Client**: `HudInput` in Supernatural mode sends a trigger on press and on release (only for a slot that has something in it; Tensura mode never triggers Bite, `SlotMode.offersBite`). `vampirism/ActionSlots` builds the six `SlotView`s from the loadout and Vampirism's own client handler on every tick: cooldown (`isActionOnCooldown`, `getPercentageForAction`, which is the fraction of the cooldown left), running (`isActionActive`), and greyed when the action is missing, locked for the faction, or `canUse` says no (`PERM` name as the reason). The **Bite slot** is `BiteView`: our own icon (`textures/gui/hud/bite.png`), the cooldown of `BiteService` counted from the press, and what `BiteRules` would do for the local player's form as its second line (`hud.bite.tooltip.<action>`) or greyed with the reason when it would do nothing. `BiteService.actionFor`, `HybridFeed.isHybrid` and `WerewolfBite.wolfForm` now take a `Player`, so the client can ask them. The client cannot run the turning rules, so for anyone in the turning who is not a werewolf it says "Finish the turning"; the server stays the authority and refuses with a reason if that was wrong. The Alt tooltips and the layer that draws all this are 13b Task 4.
- Vampirism's action icons are `<namespace>:textures/actions/<path>.png` (Werewolves too).
- Tests: `ActionGameTests` (`triggerTogglesUnlockedAction`, `secondTriggerTurnsALastingActionOff`, `triggerRespectsCooldown`, `triggerLockedRefused`, `triggerUsesLoadoutNotPacket`, `biteFiresFromItsSlot`, `movedBiteFiresFromTheNewSlotOnly`, `everyTriggerPressCountsAgainstTheRateLimit`), `ActionWerewolfGameTests` (`werewolfActionTriggers`, `hybridGetsWerewolfActions`), `SlotModeTest.biteInTensuraModeNotOffered`. The test action is the first lasting action of the faction that `canUse` allows (`werewolves:human_form` is skipped: it is "usable" for a human-form player but its toggle refuses). Mutation check: with the rate limiter forced open, the two rate-limit tests fail. **Not checked in a running client**: pressing the keys, the icons, and the tooltip text.
- `shortcut:` with the `supernatural` part off there is no hub to assign slots in, so a player's slots 2 to 6 stay empty (the plan's "show the first five unlocked actions" fallback is not built; Bite in slot 1 still works). Upgrade when a server runs `hud` without `supernatural`.

## The layer, the mode key and the Loadout tab (13b Tasks 4 and 5)

- **`AbilityHudLayer`** (registered above the vanilla hotbar layer on the mod bus, client only) draws the six `SlotView`s that `HudSlots` built this tick, so a frame does no lookups. `core/hud/HudLayout` (pure, `HudLayoutTest`) places the left column left of the offhand slot and the right column right of the attack indicator, both standing on the bottom edge; the test checks they never overlap the hotbar, the offhand slot or the attack indicator, and never leave the screen, for GUI scales 2 to 4 and 320 x 180 up. Each box: the hotbar-slot sprite, the icon (any size, `ClientIcons` reads its size once), the key in a corner at 0.7 scale, a dark fill from the top for the cooldown with the seconds, a gold outline (`textures/gui/hud/slot_active.png`) while on, a 40 % icon when greyed. **Hold Alt**: a small tooltip per filled slot (name, the mode of a Tensura skill, the cooldown or the reason). Hidden with F1, in spectator mode, with `hud_enabled` off, and when neither Tensura nor Vampirism is installed.
- **Tensura's skill HUD** is hidden through the in-memory `abilities.render` flag (no mixin; see Task 2), now fed by `AbilityHudLayer.shown()`.
- **Mode**: `hud_mode` (Alt + Caps Lock) calls `HudModeState.toggle`, which says the new mode in the action bar (`hud.mode.tensura` / `hud.mode.supernatural`) and writes it to the client `mode` setting, so it is the start mode next session. Nothing happens with one mode installed.
- **Loadout tab** (`SkillsPage` tab `LOADOUT`, `LoadoutTab`, the selection logic in `core/hud/LoadoutTabModel`, `LoadoutTabModelTest`): only when the hud part is there (the hub sees it through `shared/hud/LoadoutAccess`, never by importing the part). Left page: Bite first, then every unlocked action, with its icon and a tooltip; right page: the six slots in HUD order with their keys, an icon, a clear mark. Pick an action and then a slot, or a slot and then an action; the second pick sends `SetLoadoutPayload`. The server checks everything; a refusal comes back as an action bar line.

- **Review fixes of Tasks 1 to 3**: `HudInput` requires a mapping's own modifier to be held (`NONE` still means any modifiers, because Alt + slot key is Tensura's mode change) and does not fire a key that was already down when a screen closed (it must be seen up first); the server keeps a per-player set of held slots (`ActionService.held`) and ignores a release with nothing held (releases stay unlimited); `ActionService` refuses a sleeping player like Bite; with `next_preset_active` false Tensura's refusal comes back (GameTest).

## Final review fixes of 13b

- **Every send checks its channel.** Client: `HudSend` (no connection, or no channel for the payload on that server, means no send) is used by `HudInput` (triggers and releases) and `ClientLoadout.set`; Tensura's own activation, release and mode-change packets are guarded by `HudSend.connected()`. Server: `LoadoutService.sync` skips a player that is a `FakePlayer`, has no connection or has no channel for `LoadoutSyncPayload` (`canReceive`, like `BloodlineAccess`). GameTest `theLoadoutIsNotSentToAPlayerWithoutTheChannel`.
- **No sends after a disconnect.** With no connection (or on `LoggingOut`) `HudInput.reset()` drops `DOWN`, `PRESSED_IN`, the pending edges and `TensuraInput`'s held slots without sending anything, Tensura's release packet included.
- **Tensura's skill HUD flag is never saved as false.** javap of Tensura and ManasCore: ManasCore saves a config only when `ManasConfig.save()` or `ConfigRegistry.saveAllConfigs()` is called, and nothing in ManasCore calls the latter. In Tensura the only paths to `HudConfig.save()` are `SettingsOptions.saveAll` (from `SettingsScreen.onClose` and its buttons) and `OverlayHandler.savePositionById` / `saveScaleById` (both only from `SettingsScreen`). So while **any** screen whose class is in `io.github.manasmods.*` is open (checked each tick and on `ScreenEvent.Opening`) the player's real value is handed back, and the flag is lowered the tick after the last one closed; it is also handed back on logout and on `GameShuttingDownEvent`. Not covered: another mod that calls `saveAllConfigs` from its own screen or a timer while we have the flag lowered (none known in the pack).
- **Held presses are cleared on logout** (`PlayerLoggedOutEvent` calls `ActionService.forget`; this hook was missing before). **A release always ends the feeding** of an accepted press: `BiteService.release` calls `VampirismBite.end` whenever Vampirism is loaded, even if `actionFor` has changed (a form change) since the press.
- **A press in the tick a screen closed is ignored** (a slot key that is also the inventory key or another screen's close key). **A slot mapping with the NONE modifier also fires with Ctrl or Shift held** (Alt must work for Tensura's mode change; nothing else in the pack needs those on the same key).
- **`HudLayout`**: a column that does not fit beside the hotbar (a narrow window at GUI scale 4 or 5) is pushed against the screen edge and lifted above the 24 px hotbar strip, so it stays on screen and never covers the hotbar (`HudLayoutTest`, sizes down to 171 x 96).
## The keymap and covered keys (13a Task 4)

- `core/hud/HudKeyDefaults` (pure data) holds our defaults; `parts/hud/client/HudKeys` builds the mappings from it: `key.supernaturalbloodlines.slot_1..6` (R F V Z X C) and `hud_mode` (**Alt + Caps Lock**, `KeyModifier.ALT`), all in `PackKeybinds.CATEGORY`, context `IN_GAME`. The hub key (Home) stays in the supernatural part. **No Bite key.** The keys do nothing until 13b.
- `core/hud/CoveredKeys` (pure): the record/unbind/restore rules (see its javadoc). `KeyCover` applies them: covered ids are `tensura.keybinding.ability.slot_1..3`, `tensuraslots.keybinding.secondary_ability.slot_1..3`, `keys.vampirism.suck`, `keys.vampirism.action1..9`, `keys.werewolves.bite` (names read from each mod's lang file). It finds keys by name, so an uninstalled mod's keys are simply absent. It runs on the first client tick (NeoForge 1.21.1 has no `ClientStartedEvent`; the options are loaded and every mod has registered its keys by then), when `hide_covered_keys` changes (compared on the tick, no per-frame scan) and when the Controls screen closes (Reset All puts covered keys back on their defaults). The record is `config/supernaturalbloodlines-hud-keys.json` (an unreadable one is moved to `.bad`, never overwritten). With the part off, the main class registers `KeyCover.registerRestoreOnly()` on the client so the recorded binds still come back.
- **Never losing a bind (final review).** `KeyCover` builds a `CoverRun` (core, pure, tested with fakes) over the game's keys and a `RecordFile`. Covering writes the record **first** and touches no key if that fails (`record_not_saved`); restoring sets and saves the keys **first** and drops the record entries **after** (a crash leaves a stale record, never an unbound key with no record). `RecordFile` writes `.tmp` then `ATOMIC_MOVE`; an unreadable file is renamed `<file>.bad-<millis>[-n]` (never replaced), and while any `.bad*` file exists (or one could not be set aside) nothing is written and nothing is covered (`covering()` is false, so Controls shows the keys too). A recorded bind that cannot be parsed stays in the record. A recorded id that is no longer in `COVERED` is restored even while covering. Manual recovery is in `wiki/Key-Binds.md`.
- `KeyHiding`: **no mixin.** On `ScreenEvent.Init.Post` it removes the covered entries from `KeyBindsScreen.keyBindsList` (access transformer: `keyBindsList` and `KeyBindsList$KeyEntry.key`). Controlling 19.0.5 (read with javap): `NewKeyBindsScreen extends KeyBindsScreen`, its `NewKeyBindsList extends CustomList extends KeyBindsList`, its entries are its own `KeyEntry` (public `getKey()` from `IKeyEntry`), and `filterKeys` rebuilds `children()` from `CustomList.allEntries` (public field, `getAllEntries()`). So the same removal is done on `allEntries`, which keeps the search from bringing them back. The reserved `KeyBindsListHideMixin` stays unused. **Checked in a real dev client (2026-11-15, `runClient` with Controlling 19.0.5, Searchables and Tensura Slots in `run/mods`):** the covered keys are gone from the list and from Controlling's search (`Activation` finds nothing; `Ability` still finds Next/Previous Ability Mode and Race/Mount Ability; `category:Vampirism` lists only Minion task, Select Arrow Type, Skill Screen, Switch vision, Use Actions and Vampirism Menu), so the reserved mixin is **not** needed. Setting `hide_covered_keys = false` while the game runs logged `Covered keys: restored [...]`, put the binds back in `options.txt` (Alt modifiers kept: `key.keyboard.1:ALT`) and emptied the record; after a restart with it `false`, the search shows Ability 1 to 6 Activation with their binds (Z X C and numpad 1 2 3). Screenshots: `.superpowers/sdd/13a-keys/t13a-*.png` (not committed, the folder is ignored).
- **Alt + Caps vs the Caps radio key.** `KeyMappingLookup.getAll(key, fallback)` collects the mappings of the active modifiers for that key; the unmodified ones are added only as a fallback for a key that is itself a modifier. So Alt + Caps should fire `hud_mode` only. **Checked in a real dev client** with a temporary stand-in for the radio (a plain Caps Lock mapping in the same category, not committed): in a world, Alt + Caps fired only `hud_mode`, and Caps alone fired only the plain mapping.
- Tests: `CoveredKeysTest` (`recordsBeforeUnbinding`, `restoresPlayersOwnBind`, `restoreSkipsKeysThePlayerRebound`, `secondRunRecordsNothingNew`, `missingModIgnored`, and more), `HudKeysDefaultsTest`.

## The Bite action (R110, R20e)

Bite is an action, not a key. Nothing fires it yet: 13b Task 1 puts it in the loadout (slot 1 by default) and 13b Task 3 fires it from its slot. Until then the GameTests call `BiteService` directly. The rules are in `SPECIES-RULES.md` R110; the table is `BiteRules.decide(BiteContext)`, first match wins. `BiteService.context` builds the context: the faction id comes from Vampirism's `getCurrentFaction()`, `wolfForm` is Werewolves' `getForm().isTransformed()`, `hybridType` is `HybridFeed.isHybrid`, `inTurning` is the saved state and `turningWouldComplete` is `TurningFeed.canFeed`. Without Vampirism every press is `NONE` (`needs_vampirism`).

A press resolves the target first: in the same level (`level.getEntity(id)`, so a target in another level is "no target"), alive, not the player, within `bite_reach` (`distanceTo`), in line of sight. Then, by action:

| Action | How |
|---|---|
| `WEREWOLF_BITE` | Werewolves' own `canBite()`, `canBiteEntity(LivingEntity)` and `bite(int)` through method handles on the runtime class of the API's `IWerewolfPlayer` (`WerewolfPlayer` extends a Vampirism class that is only in the full jar). Venom (R42v) and everything else is Werewolves' |
| `VAMPIRISM_DRINK` | `determineBiteType(target)` must not be `NONE` and the vampire's level must be above 0, then `VampirePlayer.biteEntity(int)` on press and `endFeeding(true)` on release. Both are public but only in the full jar: `VampirismBite` looks them up once with `MethodHandles.publicLookup()` on the runtime class; a miss logs one warning and the bite does nothing. Vampirism's feeding runs in its own per-tick player update. Venom R42 and the bloodless refusal (`VampirePlayerBiteMixin`) still apply |
| `HYBRID_FEED` | Refused at thirst 20 (`thirst_full`) and when the victim has no blood (`no_blood`). Then `target.hurt(playerAttack(p), 2)` (the player is the direct entity, so `Venom.onDamaged` poisons a vampire victim by itself) and `HybridFeed.feed` (+5) |
| `TURNING_BITE` | `HumanLikeBlood.test(target)` or `not_human`. Then 1 damage of `supernaturalbloodlines:turning_bite` (caused by the player; the type is in the `is_player_attack` and `panic_causes` tags), the bite sound, and `TurningFeed.feed` |

A victim has blood by Vampirism's own values (`VampirismBite.blood`): a `PathfinderMob`'s `IExtendedCreatureVampirism.getBlood()` (the `entity_blood` data map); a **vampire** player's `getBloodStats().getBloodLevel()`; a **player who is not a vampire** (vampire level 0) has their **food level** (read from `VampirePlayer.onBite`, which takes `getFoodData()` below level 1; its blood stats are unused there); 0 for `BloodlessPlayers.test`. `drain` takes from the same place (`useBlood`, or `setFoodLevel`). `GameTest hybridFeedOnAHumanPlayerTakesFood`. A vampire mob and a converted creature have none. The hybrid feed **takes 2 of it** (`HYBRID_BITE_BLOOD`; a mob's `setBlood`, a player's `useBlood`) and a drained victim gives nothing (`no_blood`), so one creature cannot be farmed; the blood comes back the way Vampirism's own does. The hybrid feed and the turning bite first ask `CommonHooks.onPlayerAttackTarget(p, target)` (the attack event, which claim and PvP mods cancel; a cancelled bite is `cannot_bite_target`, with nothing drained, hurt or fed).

The biter must be alive, awake and not a spectator (`cannot_bite`, checked first). `VAMPIRISM_DRINK` reach is also clamped to the player's `ENTITY_INTERACTION_RANGE` (3), because Vampirism's `biteEntity` silently does nothing beyond it, which would otherwise look like a bite that worked and start the cooldown. Vampirism has no public feeding state to read afterwards (`getFeedProgress` is a tick counter that starts at 0), so the other silent refusals of `biteEntity` are checked before it: a dying player (`isDBNO`) and an active bat form (`isActionActive(vampirism:bat)`, untested: bat form needs unlocked skills) are `cannot_bite`. `bite_reach` is 1 to 16. One bite per 20 ticks per player (`cooldown`), set only by a bite that happened. Every refusal is an action bar line `supernaturalbloodlines.hud.bite.<reason>`. **13b:** `rate_limit_per_second` applies to every press payload, refusals included.

`BiteService.context` is private: it links Vampirism, so only `actionFor` (which checks `ModList.isLoaded("vampirism")`) reaches it. `HybridFeed.isHybrid` needs the species `isHybrid`, Werewolves loaded **and** the werewolf faction.

### Verified for 13a Tasks 2 and 3 (javap and GameTests, 2026-11-15)

- **Werewolves classes.** `de.teamlapen.werewolves.entities.player.werewolf.WerewolfPlayer` (note `entities`, not `entity`), `de.teamlapen.werewolves.api.entities.werewolf.WerewolfForm`, `de.teamlapen.werewolves.api.entities.player.IWerewolfPlayer` (its `getForm()` comes from `IWerewolf`). `WerewolfPlayer` extends `de.teamlapen.vampirism.entity.player.FactionBasePlayer`, which is not on the compile classpath (API jar only), so `WerewolfPlayer.get(p)` does not compile. Everything on it is reached through the API interface or a method handle.
- **The "wolf form" getter.** `WerewolfForm` has `isHumanLike()` and `isTransformed()`. Constructor flags: `NONE` (humanLike, not transformed), `HUMAN` (the half form: humanLike **and transformed**), `BEAST`, `BEAST4L`, `SURVIVALIST` (not humanLike, transformed). `WerewolfPlayer.canBite()` begins with `getForm().isTransformed()`, so `NONE` can never bite. **R110's "wolf form" is therefore `isTransformed()`**, not "anything but `HUMAN`": a werewolf in the half form (`HUMAN`) takes row 1, and an untransformed one (`NONE`) is row 4, which Werewolves itself refuses (`cannot_bite`). `canBite()` also needs the `BITE` permission node; `canBiteEntity` needs reach and, for a player victim, `BITE_PLAYER`.
- **Vampirism's "this creature has blood" getter.** `VampirismAPI.getExtendedCreatureVampirism(PathfinderMob) -> Optional<IExtendedCreatureVampirism>`, with `getBlood()` / `setBlood(int)` / `getMaxBlood()`. A villager has blood. A plain `IronGolem`, a `vampirism:vampire` and a `vampirism:villager_converted` have none (`setBlood` is capped by the max, which is 0). A player's blood is `IVampirePlayer.getBloodStats().getBloodLevel()` (the food level below vampire level 1), taken with `useBlood(n, true)`. Vampirism's own feeding reads the same values (`VampirePlayer.biteFeed`: `ExtendedCreature.getSafe` for creatures, `onBite` for players).
- **A FakePlayer is not ticked.** Vampirism's feeding (`updateFeeding`) runs in `VampirePlayer.onUpdate()` from the player tick, so GameTests that need the feeding to progress call `onUpdate()` themselves (`Feeding.tick`). `level.getEntity(id)` does not find a FakePlayer, so GameTests use mobs as victims.
